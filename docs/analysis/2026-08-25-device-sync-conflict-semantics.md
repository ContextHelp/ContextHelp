# Device Sync Conflict Semantics — KnowledgeObjects, Edges, Entities

> **Date:** 2026-08-25
> **Applies to:** dPKMS, ctxt
> **Extends:** [2026-08-25-device-sync-replication-survey.md](2026-08-25-device-sync-replication-survey.md)
> **References:** ADR-049, ADR-062, ADR-063,
> [2026-08-25-device-sync-requirements.md](2026-08-25-device-sync-requirements.md),
> [2026-08-04-retraction-propagation.md](2026-08-04-retraction-propagation.md),
> [2026-08-04-blob-federation.md](2026-08-04-blob-federation.md)

The survey selected op-based replication: a semantic, HLC-stamped `sync_log` replayed through per-type merge rules. This note fixes those rules — the core unsolved problem ADR-064 deferred ("Pull support will need conflict resolution strategy; ADR to follow"). Setting: one owner's concurrent edits across 2–5 devices, cooperative not adversarial. Design posture, justified by the append-mostly corpus: **a simple deterministic default everywhere, plus an explicit surfacing path for the rare conflict where determinism would erase real work** (requirements AC3/AC4).

Vocabulary used throughout: two ops are **ordered** when the later op's device had applied the earlier op before issuing; otherwise **concurrent**. Ordered ops never conflict — later wins is causally correct. The bare `sync_log` tuple carries no causal metadata, and HLC comparison is not a happens-before test (an HLC-later op may still be concurrent — HLC gives total order, not causality). Ordered-vs-concurrent is therefore decided by the fleet's **causality encoding** — one of the two §0.1 options — and every rule below that branches on it names that classifier explicitly. Every rule is commutative, associative, idempotent, and a pure function of (op + its causal metadata, state) — the properties the prototype's scripted scenarios must test, under either encoding.

## 0. Fleet-wide protocol options

Two merge-protocol parameters are fixed **per fleet at creation time** (the first device's `ctxt device init` writes them; they are the fleet's), uniform across the roster: every device runs the same option pair, the pairing ceremony validates the joiner's pair against the roster's (mismatch refuses admission), and changing either afterwards is a protocol-parameter **epoch bump** (§3) — a root-signed roster record all devices must adopt before exchanging again. Mixed-option fleets are never legal: both options change what the AC3 digest covers and how apply branches, so a mixed fleet cannot converge byte-identically.

### 0.1 `causality` — how ordered-vs-concurrent is decided

**Option SV — per-op origin sequence-vector.** Every op carries its origin device's knowledge frontier at issue time: a vector `{device → highest contiguous seq applied}` over the roster. Op X (origin A, seq i) happens-before op Y iff `Y.vector[A] ≥ i`; neither-covers-the-other = concurrent. Classification is a pure function of the two ops — stateless, satisfying §7 determinism trivially.

- *Wire cost:* O(roster) per op — 2–5 devices ≈ 10–40 varint bytes; the frontier changes rarely within a batch, so batches delta-encode (one full vector per batch, per-op diffs), amortizing to a few bytes per op.
- *GC coupling:* none beyond the existing rule — an op's causal context travels with it, so ops GC by roster ack exactly as the survey specifies; no history is retained for classification.
- *OR-set dots:* set elements tag with the add op's dot `(device, seq)`; a remove op needs no explicit dot list — its carried vector *is* the observed-set summary (the remove covers every add ≤ vector, ORSWOT-style).

**Option AR — replicated apply-records with frontier reconstruction.** Ops carry only `(device, seq, hlc)`. The `sync_log` additionally replicates **apply-records**: periodic frontier checkpoints ("device B's frontier at own-seq j was V") plus per-op apply entries between checkpoints. X happens-before Y is reconstructed by looking up origin(Y)'s frontier as of Y's seq and testing coverage of X.

- *Wire cost:* minimal per op (fixed ~16 bytes), plus the apply-record stream — O(applied ops), compressed by checkpoint interval; total volume comparable to SV but shifted from ops onto records.
- *GC coupling:* a second retained stream — apply-records must outlive every op that might still be classified against them, so record GC ties to the same causal-stability rule *and* to conflict-window closure; a fresh or long-offline device must reconstruct frontiers from checkpoints before it can classify anything.
- *OR-set dots:* removes must enumerate their observed add-dots explicitly (the op carries no vector) — O(observed adds) per remove.

**Recommended default: SV.** The roster is capped small (2–5, ceiling ~10), so SV's per-op overhead is bytes, not structure; classification needs no lookaside state, which keeps apply a pure function of (op, state) exactly as §7 demands; and GC stays single-stream. AR earns its complexity only for rosters or op volumes where per-op vectors dominate payload — neither is this design center.

### 0.2 `conflict_copy` — where deterministic-rule losers live

**Option R — replicated truth.** Losers are part of replicated state and of the AC3 digest. A losing concurrent content edit (§1.2) materializes as a corpus conflict-copy object; a delete-class loser (§1.3, §2, §3) materializes as a parked row in `sync_conflicts` (§5). Both materialize **deterministically on every replica, with no extra wire traffic**: the artifact id is a pure function of the losing op — `uuidv5(ns=sync-conflict, origin_device ‖ origin_seq)` — so every device that applies the same concurrent pair mints the identical artifact and digests agree. (The alternative — a designated emitter shipping the copy as an ordinary create — is rejected: the emitter may be offline or revoked at the decisive moment, and derived-id determinism already removes the need.)

- *AC3 digest rule:* the digest covers corpus objects **including** conflict copies, plus the `sync_conflicts` table (rows and their resolution stamps).

**Option L — local-only surfacing.** Losers never enter replicated state. Every replica still *detects* each conflict (apply is deterministic, so every device that merges the same concurrent pair observes it), but the loser parks only in the local `sync_conflicts` table; no corpus conflict-copy objects exist under this option — edit×edit losers park like delete-class losers.

- *AC3 digest rule:* the digest **excludes** `sync_conflicts` entirely and covers winner-only corpus state. Resolution that emits ordinary ops (§5) replicates as usual, but each device dismisses its own parked row independently.

**Recommended default: R.** AC4's promise — the loser is preserved and surfaced — should itself survive device loss and be actionable once for the fleet, not once per device. R gives resolve-anywhere semantics and makes the hub the natural review surface (its whole T1 role: copies and parked rows reach it). L buys a cleaner corpus and a smaller digest at the cost of per-device re-review and losers that die with a device — the right trade only where conflict payloads must not propagate, which is why it remains an option rather than being dropped.

## 1. KnowledgeObjects

### 1.1 Identity across devices

**Replication identity is `objects.id` — the durable id — never `content_hash`.** The federation stream keys on `content_hash` and therefore forks silently on edit ([2026-08-04-retraction-propagation.md](2026-08-04-retraction-propagation.md): "Corrections silently fork instead of superseding"); device sync must not inherit this. `id` is minted once at capture, never changes, and is the subject of every op.

The two unique dedup indexes remain locally enforced and become *merge inputs*:

- **`content_hash` collision (UNIQUE, `migrations/003_content_hash_reinforcement.sql`):** two devices independently capture the same content → two ids, one hash. Replaying the remote `object.create` trips the unique index; the merge rule converts it: the create with the **lower HLC is canonical** (deterministic on every device); the other id is recorded in a new `object_id_aliases` table (`alias_id → canonical_id`; the existing `aliases` table, `migrations/010_aliases.sql`, maps *names*, not ids — different job); the losing create is degraded to a `reinforce` op on the canonical id. Subsequent ops addressed to an aliased id resolve through the alias before apply. No data lost, no duplicate row, reinforcement semantics preserved.
- **`source_key` collision (`migrations/026_source_key.sql`):** same external artifact (same Slack ts, same message-id) captured on two devices — same rule: lower-HLC create canonical, other aliased, metadata merged per §1.2.

**Order independence — the canonical flip.** "Lower HLC is canonical" must hold regardless of arrival order. When the lower-HLC create arrives at a replica that already applied the higher-HLC create — and that resident row has since accreted edges, graph nodes, or `sync_conflicts` references — the arriving create wins retroactively: in one transaction the canonical row is written under the winner's id carrying the field-wise merge of both states (§1.2), every row referencing the resident id (edge endpoints, `sync_conflicts.object_id`, existing alias targets) is rewritten to the canonical id, and the resident id lands in `object_id_aliases`. This **alias-normalization of written rows** is required because AC3 demands byte-identical tables: resolving through the alias at read time would leave arrival-order-dependent bytes on disk. §7 pins the scenario (late-arriving lower-HLC create against an accreted resident).

**Edits supersede, never fork (AC6).** `object.edit` carries `{id, new_content, prior_content_hash}`; apply rewrites content in place, recomputes `content_hash`, and records the old→new hash supersession locally (the record federation's future `corrected` tombstone needs — same fact, one write). The id is stable through any number of edits on any devices.

**Edit into a hash collision.** The recomputed `content_hash` can trip the UNIQUE index against a *different* live object. The rule is the create-collision rule generalized: whenever two live rows would share a `content_hash`, the row whose **create op has the lower HLC** is canonical; the other id is aliased into it, states merge field-wise (§1.2), edges and nodes union, and the triggering op is additionally recorded as `reinforce` on the canonical id. The same pure function fires whichever side arrives second (the edit, or the other object's create), so replicas converge in every arrival order. §7 pins both orders.

### 1.2 Field-class merge matrix

| Field class | Fields (`migrations/001_initial.sql` + later) | Rule for concurrent ops |
|---|---|---|
| **Capture immutables** | `id`, `type`, `subtype`, `source`, `source_key`, `created_at` | Written once at create; no op mutates them → conflicts impossible. Divergence here means an identity bug: surface to anti-entropy repair, never merge. |
| **Content registers** | `raw_content`, `content_type` | LWW by HLC **with loser preservation** (concurrency per §0.1): concurrent `object.edit` × `object.edit` → higher HLC wins the row; the loser is preserved per the fleet's §0.2 option — corpus conflict copy under R, parked row under L (§5). The only field class where the deterministic rule can erase real work, hence the only one that pays for surfacing. |
| **Curation scalars** | `status`, `inbox_note`, `profile_id` | LWW by HLC, with the status exceptions in §1.3. Cheap, reversible, and any race is between two decisions the same owner made — latest intent is the honest default. |
| **Accretive sets** | `graph_json` nodes — the tag / mention / summary / section / decision / task node classes, stable node UUIDs per ADR-063 | **OR-set, add-wins, with semantic-identity dedup**: union keyed by node UUID, then deduplicated by semantic identity `(node_type, canonical payload hash)` within the object — the same shape edges get from `(from,to,type)` (§2). Two devices running the same enrichment mint *different* UUIDs for the same semantic node; without dedup the union duplicates it. On a semantic collision the lower-HLC add's UUID is canonical, the other add degrades to a no-op (its UUID recorded as a node alias so later per-node ops resolve). With dedup in place, concurrent enrichment merges without loss or duplication — the dominant "conflict" in an append-mostly corpus, resolved with zero user attention. A remove deletes only the add-dots it observed (dot mechanics per §0.1). Per-node *mutation* (rare; nodes are append-typed) is LWW by HLC within the node. Intra-object `graph_json` edges follow their endpoint nodes. |
| **Counters** | `reinforcement_count` | Sum of `reinforce` ops (op-based counter — replay gives exact counts, no max() approximation); `last_reinforced_at` = max HLC. |
| **Derived, never synced** | `fts_indexed`, `vector_indexed`, `embeddings`, `objects_fts` rows, vec0 rows | Not in the op vocabulary at all (§4). |
| **Legacy flat columns** | `sections`, `tags`, `decisions`, `tasks` JSON columns | Projection cache per ADR-063 — regenerated from merged `graph_json`, never merged directly. (The flat `tags` column is *only* this projection; tags merge exclusively as tag nodes in the accretive-set class above — one merge class per fact.) |

**Persisted merge clocks.** Every LWW rule above must survive op GC: once the deciding ops are pruned by roster ack, a late comparison (anti-entropy repair, epoch resync, an option-AR reconstruction gap) still needs the clock that last wrote each field group. The schema therefore persists **per-row, per-field-group HLC columns** — on `objects`: `content_hlc`, `status_hlc`, `note_hlc`, `profile_hlc`; on `edges`: `attr_hlc` (for `weight`/`metadata`, §2); on `entities`: per-field clocks in an `enrich_hlc` JSON map (§6) — written in the same transaction as the field they stamp. OR-set elements persist their add-dots per §0.1. The anti-entropy state digest (survey §2.C) hashes these columns alongside the fields they govern; there is no single "per-row HLC".

### 1.3 Status transitions as a lattice with two exceptions

Live values: `inbox` → `active` → `discarded` (`internal/storage/types.go:105`, default `active`; the ADR-062 lifecycle's captured/curated/discarded). Rules for concurrent status ops — concurrency decided by the §0.1 classifier in every rule:

1. **Status × status → LWW by HLC.** Two explicit dispositions by the same owner: take the later. Deterministic, reversible (status is not deletion), and any lattice we could impose (e.g. discard-anywhere-wins) would sometimes override the owner's *more recent* decision — worse than honest LWW.
2. **Discard × content-edit → edit revives.** `set_status(discarded)` on A and `object.edit` on B, *classified concurrent* (§0.1 — an edit that causally follows the discard revives by ordinary later-wins apply, no exception needed): the edit wins; the object lands `active` with B's content; the discard is parked as a suggestion in `sync_conflicts` (§5), not applied. Rationale: an edit is invested work, a discard is a cheap reversible flick; the asymmetric rule loses nothing (the discard suggestion survives) while discard-wins would bury a fresh edit. This is deliberately the *opposite* of the deletion rule —
3. **Delete (tombstone) × anything-concurrent → delete wins** (§3). Deletion is destructive intent and resurrection is the S4 threat; concurrent edits are preserved as payload-bearing parked rows in `sync_conflicts` (§5) — never as corpus objects, which delete-wins forbids.

The pair (2)/(3) is the design's sharpest choice: *discard is revivable, delete is not*. It gives users a safe verb (discard) and a strong verb (delete) with predictable sync behavior for each.

## 2. Edges

Inter-object edges are the relationship source of truth (ADR-049; `edges` table, `migrations/001_initial.sql:48-58`).

- **Semantic identity:** `(from_type, from_id, to_type, to_id, edge_type)`. The `id` column is instance-minted; concurrent `edge.add` of the same semantic edge on two devices → one edge, **lower-HLC op's id kept**, the other add degrades to a no-op (after id-alias resolution of endpoints). Idempotent by construction.
- **Set semantics: OR-set, add-wins.** `edge.remove` removes only observed adds — a re-add concurrent with a remove survives. Matches user expectation: "I linked these on my laptop" should not be silently undone by an unrelated removal race on the phone.
- **`weight`, `metadata`:** LWW by HLC per edge; no surfacing (derived/advisory values, cheap to recompute — many are pipeline-written).
- **Dangling-edge rule: referential integrity beats add-wins.** `edge.add` concurrent with a tombstone on either endpoint (§0.1 classifier; an add causally after the tombstone is refused outright as a bug — the issuer had applied the delete): the edge is **not** applied (or is cascade-removed when the tombstone arrives second — order-independent outcome, same final state). The suppressed edge parks in `sync_conflicts` with its full op payload (§5), referencing the surviving endpoint, so deliberate intent ("this was linked to the thing you deleted elsewhere") is visible rather than silently swallowed. Aligned with the local cascade (`Service.DeleteObject` deletes edges before the object; FK `ON DELETE CASCADE` on adjacent tables) and with delete-wins (§1.3.3).

## 3. Deletions and tombstones

- **Discard is not deletion.** Discard = `set_status` op (§1.3), revivable, content retained. Delete = `object.delete` op producing a **tombstone**; apply invokes the atomic local purge — row, edges, FTS entry, vec row, embeddings, blob refs — the primitive the retraction note names as prerequisite ([2026-08-04-retraction-propagation.md](2026-08-04-retraction-propagation.md): "Even local deletion is incomplete"). Device sync shares this dependency; it is on the foundation checklist.
- **One tombstone table, two consumers.** The retraction note's `Tombstone{ObjectID, ContentHash, Reason, SupersededBy, Scope, IssuedAt, Signature}` gains `hlc` and `origin_device`. A deletion is one fact; federation (outbound retraction) and device sync (roster convergence) are two propagation channels over the same row — parallel tables would let the same deletion exist in one and not the other.
- **Resurrection prevention (AC5/S4):** the tombstone outlives the row. Incoming ops addressed to a tombstoned id, classified per §0.1: concurrent-with-tombstone → suppressed, parked payload-bearing in `sync_conflicts` (delete-wins); causally *after* the tombstone (the issuing device had applied the delete; user re-captured) → legitimate new object (new id, new create — nothing to suppress). A lagging device's re-push of the dead object's create/edit is suppressed by id, not content-hash, so an *independent* later capture of identical content on a clean id is allowed — deletion retracts *that object*, not the content forever (same posture as blob-federation §4: tombstones retract rows, not bytes).
- **GC by causal stability over the roster.** The same-owner advantage over open federation: the peer set is enumerable. A tombstone is GC-able when `min(acked HLC over active roster devices) > tombstone.hlc` **and** a retention floor has passed (default 90 days per the retraction note; the exact-roster argument may justify shorter — operator-tunable). **Revoked devices leave the min** (else a stolen phone blocks GC forever); a device *unrevoked but silent* past the floor is flagged to the owner rather than silently dropped from quorum.
- **Returning past the horizon:** epoch rule (retraction note §3). A device whose last ack predates a tombstone-GC epoch bump reconciles by full resync: current merged state wins; the device's never-synced local ops replay on top through these same rules; its stale rows cannot resurrect because they arrive as state, not ops, and state reconciliation is digest-driven repair (survey §2.C anti-entropy), which takes the epoch side.
- **Epoch authority: per-device for GC, root-signed for parameters.** No global epoch counter coordinates the hubless mesh, and none is needed. Each device advertises its own **GC frontier** — the HLC below which it has pruned ops and tombstones — in every handshake; frontiers are per-device and monotone. The epoch test is pairwise: a peer whose acked position against me predates my GC frontier cannot be served by op replay and takes the digest-driven full-resync path. The hub changes nothing semantically — it merely holds the most complete log, so fewer of its syncs degrade to resync. The only *global* epoch is the protocol-parameter epoch (§0), bumped exclusively by a root-signed roster record, because parameter changes must land atomically fleet-wide or convergence breaks.
- **Ack-vector regression = restored backup.** Every peer persists, per roster device, the high-water mark it has observed for that device: its own max seq and its acked vector. A device presenting a *lower* own-seq or a regressed vector than its persisted high-water is running restored state — requirements S4's "stale replica wearing a valid key". Detection is mandatory at handshake; the response is refuse-normal-exchange plus epoch resync: current merged state wins, the device fast-forwards its own seq counter past the observed high-water (burned seqs are never reused — reuse would alias two distinct ops under one dot), and its genuinely new post-restore writes replay on top.

## 4. Derived state — the invariant, confirmed

**FTS rows, vec0 rows, and embeddings never appear in the op vocabulary and are never merged.** Each applied op runs the same per-object index maintenance as a local write (the `Update` path already maintains FTS + vec; ADR-070 bucket-1 semantics), so post-sync rebuild cost is O(applied ops). Embeddings are deterministic per (content, model): a device may ship them as an *optional cache hint* alongside ops (they already travel in federation pushes — [2026-08-04-blob-federation.md](2026-08-04-blob-federation.md) "text_content and embeddings do travel"), but a receiver treats a hint as untrusted-if-absent: correctness never depends on it, and a model-version mismatch (`embedding_models` registry, ADR-071) discards the hint and recomputes. `index_signatures` (per-table, ADR-070) stay strictly local — two devices on different pipeline versions converge on *content* and each rebuild their own indexes.

Blob bytes: out of scope here (identity/transport note states the requirement; design defers to [2026-08-04-blob-federation.md](2026-08-04-blob-federation.md) Option C). The op stream carries the ref and the manifest entry; bytes move content-addressed and lazily.

## 5. Conflict surfacing

Where a deterministic rule discarded information, the loser must be preserved *with its payload* and made visible (AC4). Two artifact kinds, switched by the §0.2 option:

- **Parking table — `sync_conflicts`, payload-bearing.** `resurfacing_queue` cannot carry a preserved loser: its `object_id` is `NOT NULL REFERENCES objects(id) ON DELETE CASCADE` and it has no payload column (`migrations/017_resurfacing_queue.sql`) — a delete-wins purge would cascade away the very row meant to preserve the concurrent edit, and a payload-less queue row preserves nothing anyway. `sync_conflicts` is its own table: `(id TEXT PK — derived per §0.2, class TEXT, object_id TEXT NULL — deliberately no FK, losing_payload JSON, losing_op_device, losing_op_seq, losing_hlc, created_hlc, resolved_at, resolution)`. It parks delete×edit losers (§1.3.3, full edit payload), suppressed discards (§1.3.2), suppressed dangling edges (§2), and — under option L — losing content edits too. Rows reference dead ids without an FK on purpose: they are the record that outlives the object.
- **Conflict copies — option R, edit×edit only.** A losing concurrent content edit is preserved as a sibling corpus object: same `type`, **deterministically derived id** (§0.2 — identical on every replica, no designated emitter), tagged `sync-conflict`, linked `conflicts_with → winner` in `edges`, status `inbox` — surfacing through the normal inbox/review flow instead of a bespoke UI, excluded from default `active` search (`types.go:105` status filtering) without being hidden. Syncthing's `.sync-conflict` files prove the pattern; CouchDB's preserved losing revisions prove the posture. Under option L this bullet is inert: edit×edit losers park like everything else, and the corpus holds winners only.
- **Surfacing.** `ctxt sync conflicts` lists open parked rows and copies. Live-object classes (suppressed discard, dangling edge) may additionally enqueue a pointer into `resurfacing_queue` with `reason = "sync-conflict:<class>"` — their subject object exists, so the FK holds. One `system_reminders` entry per sync batch that produced conflicts (not per conflict — no notification storms).
- **Resolution is ordinary ops.** `resolve --keep-mine|--keep-theirs|--merge` emits normal `object.edit`/`set_status`/`edge.add` ops — resolution replicates like any other write, and the wire has no special resolution verb; a resolving op carries the parked row's id as an annotation, so applying it stamps `resolved_at` deterministically. Under option R that stamp converges fleet-wide (resolve once, resolved everywhere); under option L each device clears its own row. In topology T1 the hub is the natural review surface under option R (copies and parked rows reach it); any device can resolve in either option.
- **Audit.** Every applied remote op and every conflict decision (automatic or user) appends to `audit_log` (`migrations/011_audit_log.sql` — append-only by trigger), satisfying AC12 and making "why does this object look like this" answerable after the fact.

## 6. Entities

Entities are keyed by natural key `slug` (PK, `migrations/001_initial.sql:36-45`) — no cross-device id problem. Three provenance classes, three rules:

- **Registry-sourced** (`registry_url != ''`, `migrations/013_entity_thin_sync.sql`): the registry is authoritative; rows arrive via registry sync on every device independently. Device sync does **not** carry them — replicating would race the registry and entangle two protocols. `content_status`/`version_hash` stay local-per-device.
- **Locally derived from mentions** (extraction pipelines): re-derivable at will — ADR-064 already classifies entities as "derived — re-extracted at target". Device sync carries them only implicitly: objects and mention edges sync, and local re-derivation converges. `UpsertThin`'s existing redundancy tolerance (used by both federation receive and registry sync) absorbs double-derivation harmlessly.
- **Owner-curated enrichment** (manual description edits, alias additions, metadata): the part that must sync — it is work, not derivation. `entity.enrich` ops: `description`/`title`/scalar `metadata` keys are LWW registers by HLC; `aliases` is an OR-set union. No conflict copies for entities: scalars are short, low-stakes, and re-editable; LWW loss here does not meet the surfacing bar (posture: deterministic default, surface only where work would vanish).
- **Deletion:** entity tombstones only for curated entities; a derived entity deleted on one device while mentions still exist elsewhere simply re-derives — deletion of derived state is local hygiene, not a replicated fact.

## 7. Determinism obligations (test contract)

The prototype's scripted scenarios (foundation note) must pin, per rule above, the invariant *apply(opA, apply(opB, S)) = apply(opB, apply(opA, S))* and idempotence *apply(op, apply(op, S)) = apply(op, S)* for: create×create same content-hash; late-arriving lower-HLC create against an accreted resident row (canonical flip, §1.1); edit tripping `content_hash` UNIQUE against a different live object, both arrival orders (§1.1); edit×edit same object; node.add×node.add same semantic node, different UUIDs (§1.2); status×status; discard×edit; delete×edit; delete×edge.add; edge.add×edge.add same semantic edge; edge.remove×edge.add; enrich×enrich same entity; reinforce×reinforce. The full matrix must pass under each causality encoding (§0.1) and each conflict-copy option (§0.2) — the implementation carries both alternatives of each even though any one fleet runs one pair. Apply must be a pure function of (op + causal metadata, state): no wall-clock reads, no config-dependent branches beyond the fleet option pair, no map-iteration-order dependence in `graph_json` merge.

## Open questions for the ADR

1. Whether `object_id_aliases` rows ever GC (safe once no device holds ops referencing the alias — same causal-stability rule; cheap to keep forever).
2. Whether the discard-vs-edit exception (§1.3.2) extends to `inbox_note` edits (currently: no — note edits are curation scalars, LWW).
3. Conflict-copy retention: auto-expire unresolved copies (e.g. 180 days) or keep until acted on (leaning: keep — they are ordinary objects, the corpus is the archive).
4. Whether `profile_id` moves need a guard (concurrent move to two different profiles → LWW; a profile-scoped visibility surprise, maybe worth a parked `sync_conflicts` suggestion).
