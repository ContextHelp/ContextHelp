# Decentralization as a Third Frame? — Coverage Assessment

> **Date:** 2026-08-04
> **Applies to:** dPKMS, ctxt
> **Extends:** [2026-08-04-storage-architecture-pov.md](2026-08-04-storage-architecture-pov.md) (PKMS frame), [2026-08-04-storage-federation-addendum.md](2026-08-04-storage-federation-addendum.md) (federation frame)

The question: `docs/dpkms/decentralization.md` names four goals — user ownership, modularity + interoperability, federated knowledge models, privacy by design. The [federation addendum](2026-08-04-storage-federation-addendum.md) examined sharing, sovereignty, distribution, and access control. Did it thereby exhaust "decentralization" as a lens on storage, or is there a residual frame with its own concerns? Verdict at the end; the audit goal-by-goal first.

## Goal 1: User ownership — covered

Fully covered by the two existing write-ups. The [base assessment](2026-08-04-storage-architecture-pov.md) establishes one-file-one-owner as the core bet; the federation addendum promotes it to "the sovereignty boundary itself" and works through its consequences (daemon as policy boundary, retraction, key lifecycle). Nothing to add.

## Goal 2: Modularity + interoperability — partially covered, two new concerns

The decentralization doc's strongest claim is that *independent parties* can ship registry, pipeline, and storage implementations with no central ontology. The federation addendum examined none of the storage implications of this; its conformance-suite point was about SQLite/Postgres parity between the two *first-party* drivers.

**NEW — the plugin backend contract is paper.** ADR-021 specifies a `RegisterStorageProvider` surface, capability flags (`SupportsFullText`, `SupportsVectors`, …), and graceful degradation so third parties can ship BoltDB/Neo4j/LEANN backends. None of it exists: there is no provider registry anywhere in `internal/` or `pkg/`, and config validation admits exactly `sqlite` and `postgres`. That is a defensible sequencing choice (the base assessment praised not paying for hypothetical backends), but it means a headline decentralization goal — storage implementations by independent entities — currently has **no storage-side surface at all**, and worse, no conformance contract for the day it does. Two first-party drivers already risk drift without a shared test suite; N third-party backends with self-reported capability flags is that problem raised to a power. The interface (~24 narrow stores) is the de facto contract, but it is unpublished, unversioned, and untestable from outside the repo.

**NEW — sandboxing constrains the process, not the stored claim.** Third-party pipeline steps *are* isolated at execution time (ADR-027/055): `internal/steps/executor.go` applies process- or container-level resource limits, filesystem read-only mounts, and network denial. But the step's output is a mutated draft `KnowledgeObject` that is persisted with the daemon's full storage rights. The schema records provenance only at object granularity (`pipeline`, `source`, `registry_influences`, `plugins` columns) — nothing binds a specific tag, mention, or edge to the step that produced it, and no write-scope limits what a sandboxed step may assert (arbitrary entities, arbitrary graph edges, arbitrary tags feeding search ranking). A malicious or buggy third-party step cannot escape its container, but it can silently poison the knowledge graph. Execution isolation without influence provenance is half a trust boundary.

**Schema-registry interop — mostly covered, one gap.** The registry schema (`docs/dpkms/schema-registry.md`) is versioned, deterministic, and append-friendly; storage caches manifests (`registry_cache`) and entitlements (`registry_entitlements`) sensibly. The gap: stored tags carry no record of which taxonomy *version* produced them. The index-signature mechanism the base assessment praised tracks tokenizer and embedding-model provenance — but not registry/taxonomy versions. A major-version taxonomy bump or an unsubscribe leaves orphaned canonical IDs in `objects.tags` with no invalidation path, the exact silent-rot failure the index signatures were built to prevent for the other indexes.

## Goal 3: Federated knowledge models / agent worldviews — the real hole

The federation addendum federated **bytes**: blob refs, watermarks, retraction tombstones, signatures. It never examined federating **meaning**, and this is where the storage schema makes its strongest unstated assumption.

**NEW — the schema assumes one resolved ontology per instance.** The `entities` table is keyed by bare `slug`; `namespace` is a default-empty column, and `registry_url` (added for thin sync) holds a single value. When multiple subscribed registries define the same slug, `internal/registry/reconcile.go` collapses them to **one winner** per instance (last-write-wins or trust-score, with conflict reports as a side channel). Contrast the docs' promise: agents operate in *scoped worldviews* — different registry subscriptions per agent, "no shared universal ontology required." Storage cannot represent that. Objects gained `profile_id` scoping; entities did not. Two agents with conflicting registry subscriptions share whichever entity definition won reconciliation. The deterministic-merge machinery is genuinely good *for producing a single overlay*; the schema just has nowhere to put a second one.

**NEW — entity identity does not survive federation.** Mentions travel as bare slugs. When instance A subscribes to instance B's content, B's `@stripe.api.checkout` arrives into A's flat slug namespace, where A may hold a same-named entity from a different registry with different semantics. There is no origin-qualified entity identity (no `(origin_instance, namespace, slug)` key, no content-addressed entity IDs), so cross-instance slug collision is resolved by accident — whichever row exists wins, and backlinks from federated objects silently attach to the local impostor. The federation addendum's ownership-anchored model ("every object has one authoritative home") solves this for *objects* but was never extended to *entities*, which are precisely the things two instances are most likely to name identically while meaning differently.

## Goal 4: Privacy by design — partially covered, two new concerns

The federation addendum covered retraction propagation and named it the load-bearing privacy commitment. Correct, but retraction is the *outbound* half. Two inbound/at-rest aspects went unexamined.

**NEW — ADR-019 encryption is entirely unimplemented, and the search design fights it.** No encryption code exists in `internal/storage`: no encrypted-object columns, no blind index table, no SQLCipher wiring. That alone is a status observation, not an architecture flaw. The architectural point is that the base assessment's most-praised decisions — whole-object embedding, FTS5 and vec0 living inside the same database — are in direct tension with ADR-019's selective-encryption model: an encrypted object cannot appear in the FTS index or the vector index as designed, and the blind-index scheme has no semantic-search analog at all (ADR-019 concedes this). Selective encryption is therefore not a deferred feature but a pending **design collision**: retrofitting it will either carve encrypted objects out of search entirely (surprising the user who encrypted their most important notes) or force a searchable-encryption scheme the current index architecture has no seam for. Deciding this before the schema calcifies further is cheap; after, it is not.

**NEW — scatter-gather leaks query patterns to registry operators.** `internal/registry/bookmark_search.go` sends the raw query string (`GET <registry>/bookmarks/search?q=<query>`) to every subscribed registry concurrently. The decentralization doc's invariant is "registries never receive user content" — but queries *are* content: search patterns reveal interests, projects, and activities (ADR-019 names exactly this risk, then answers it only with TLS, which protects transit, not the operator). A user subscribed to a commercial registry ships them a keystroke-level interest profile. Mitigations exist at several price points (local-index-only search against synced registry indexes, query batching/generalization, opt-in per-registry remote search) but today the behavior is silent and default-on wherever remote search is enabled. The federation addendum's access-control analysis covered who may read *your* instance; it never covered what your instance tells *theirs*.

## Verdict

**Decentralization is not fully subsumed — but the residual is narrower than a full third frame.** The federation lens genuinely absorbed user ownership and the distribution mechanics (sync, sovereignty, access control, retraction). What it never touched is the **semantic and extensibility layer**: who defines meaning (ontologies, entity identity), who is allowed to write it (plugin backends, third-party pipeline provenance), and what the instance discloses while consuming it (query leakage, encryption posture). Call the residual frame **semantic decentralization** — distribution of *meaning and trust* rather than distribution of *bytes*. It reorders nothing in the federation addendum's risk list; it appends to it. The two frames meet at one point: entity identity across instances is simultaneously a federation mechanic and an ontology problem, and it is currently owned by neither.

Recommended follow-up investigations (described, not scheduled):

1. **Entity identity and namespacing** — design an origin-qualified or content-addressed entity identity model; decide whether `entities` needs `(namespace, slug)` or worldview-scoped keys; specify collision behavior for federated mentions. Highest priority: it blocks both agent worldviews and safe federation.
2. **Worldview-scoped semantics in storage** — determine whether per-agent/per-profile registry overlays need first-class storage representation (scoped entity views, per-worldview reconciliation) or can remain a query-time projection over conflict reports.
3. **Encryption × search collision** — decide the searchability semantics of encrypted objects *before* implementing ADR-019; evaluate whether whole-object embedding survives selective encryption or needs an encrypted-corpus carve-out.
4. **Remote-search privacy posture** — audit every outbound code path that transmits user-derived strings to registries; define a default (local-index-only) and an explicit opt-in for remote query fan-out.
5. **Plugin backend conformance contract** — before any third-party backend exists, publish the store-interface contract as a versioned, externally runnable conformance suite (the same suite that fixes SQLite/Postgres parity drift), including capability-flag verification.
6. **Influence provenance for third-party steps** — evaluate per-field or per-assertion provenance (which step/plugin produced which tag/edge/mention) so sandbox execution isolation is matched by data-lineage accountability, and taxonomy-version stamps join the index-signature family.
