| `refactor(cli)!: drop the ctxt profile default alias` | `none` | no | no | n/a | **BREAKING**: `ctxt profile default` is gone and fails as an unknown command (exit 2). Use `ctxt profile set <profile>` to pin the default and `ctxt profile unset <profile>` to clear it |

## Changes by bucket

### `reindex_auto` changes

#### Re-projection on a projection change

- **What changed**
  - Each object records the projection version its full-text body was built with (`objects.projection_version`). Ingest and updates stamp the current version.
  - When the `objects_fts` signature doesn't match on startup, `dpkms serve` queues a background job (`projection:reproject`). It rebuilds each stale object's full-text body and index entry from the stored object, then stamps the signature. It does not re-run pipelines or call a provider.
  - Startup no longer stamps a mismatched signature. The mismatch stays until the job has re-projected every object, so a run cut short is picked up again on the next start.
  - Progress: `ctxt upgrade status` shows bucket `reindex_auto` with target `projection@v2`, `done`/`total`, and `failed`. Bus events are `dpkms.upgrade.reprojection.{scheduled,started,progressed,completed,failed}`.
- **Signature bump**: migration 040 (Postgres 18) clears the stored `objects_fts` hash. Rows written before it carry no stamp, and databases that ran the 2026-09-26 release had already stamped the `v2` signature over bodies built by `v1`. On the first start after this release, every object is re-projected once. That run applies the repeated-segment fix from 2026-09-26 to stored objects.
- **Estimated wall-clock**: one short transaction per object and no model calls, so it runs at local write speed. Not measured on a large corpus; expect it to scale with object count. Search keeps serving: each object switches to its new text as it is reached.
- **Resume and failures**:
  - A run stopped by shutdown, crash or `dpkms job cancel` resumes on the next start with the objects not yet done. Finished objects are not redone.
  - An object that can't be re-projected is counted, left with its old text, and retried on the next start. `ctxt upgrade status` stays `failed`, with `last_error` naming the first failure.
- **Not refreshed: embeddings.** Stored vectors keep the text they were embedded from, including the doubled segments from before 2026-09-26. This job doesn't re-embed.
- **Concurrent work**: ingest during the run is safe. New and updated objects are written with the current projection and skipped by the job. While an embedding migration holds the upgrade status, the re-projection waits for it to finish.

#### Externalized content indexed as text

- **Before.** Content above `storage.blob.threshold` is stored as a `blob://<key>` ref. Storage copied that ref into an empty `text_content`, so full-text search indexed the ref (an object matched `blob` and its key, not its own words), and an embedding migration embedded it.
- **Now.** `externalize_content` keeps the first `storage.blob.threshold` bytes of the content inline as `text_content`, flagged `metadata.text_content_truncated`: search and embeddings index that text. `GET /objects/{id}` still returns the whole content as `text_content`. A `blob://` ref is never indexed or embedded: projection `v3` drops it wherever it sits.
- **Indexed text is capped.** Search finds an externalized object by the words in its first `storage.blob.threshold` bytes (default 64 KiB), plus its summaries and sections.
- **Objects externalized earlier.** Their `text_content` holds the `blob://<key>` ref. The re-projection (projection `v4`) resolves each ref from the blob store and stores the content's first `storage.blob.threshold` bytes as their text, as `externalize_content` does now, before re-indexing. `ctxt upgrade status` shows the run as `projection@v4`; the job's result line counts the repaired objects and the ones whose blob could not be read (logged with their ID; they keep the ref).
- **Action**: see the operator impact row.

### `none` changes

#### Search on dpkms

- **MCP**: the `search` tool runs `POST /api/v1/find`'s search, `hybrid` by default. It takes `mode` (`hybrid`, `fts`, `vector`), `profile`, `min_score` (hybrid only) and the facet filters (`since`/`until` as `YYYY-MM-DD`), and returns titles, snippets and scores. Its description no longer claims hybrid while running RSQL.
- **No embedding model or provider**: the tool answers from full text and says so (`executed_mode` `fts_only` or `fts_fallback`, `diagnostics.semantic`).
- **Profiles**: full-text, vector and hybrid search now honor a profile on SQLite and Postgres. `POST /api/v1/find` and the MCP tool take `profile`; leaving it out searches every profile. Postgres now stores each object's profile. The caller chooses the profile; it is not an access control.

#### Search graph on dpkms

- **REST**: `GET /api/v1/search/graph` returns the hybrid search trace as a JGF document (`ctxt.search-graph/v1`), the one `ctxt find --graph --format json` prints. Parameters: `q`, `profile`, `limit` (default 10), `min_score`, `POST /api/v1/find`'s filters, `max_nodes` (default 250, at most 1000), `max_edges` (default 1500, at most 10000), `similar`, `similar_threshold`. The body is the bare document, not `{data, total}`. See [api-rest.md](../api/api-rest.md#get-searchgraph).
- **Entitlements**: entities in namespaces the caller is not entitled to are left out entirely, including from `co_mention` weights and counts. Not metered, like search.
- **No embedding model or provider**: `200` with a full-text-only graph (`metadata.mode` `fts_only` or `fts_fallback`).
- **Web UI**: `/ui/searchgraph/?q=<query>` shows the graph in the viewer `ctxt find --graph` opens. The page's query string goes to `GET /api/v1/search/graph` unchanged; a click on an object links to `/ui/objects/<id>`. `/ui/searchgraph` redirects there with the query kept. Same headers as the rest of `/ui` (no framing, `nosniff`, `no-referrer`), plus the page's own Content-Security-Policy: same-origin scripts, styles and requests only. Works on private instances and behind a reverse proxy that signs you in; instances that check tokens themselves refuse the graph request (`401`) until the web UI can sign in. See [search-graph.md](../manual/workflows/search-graph.md#open-it-in-the-web-ui).

#### Config write commands

- **Only the edit is written.** `ctxt setup`, `ctxt profile create|rm|set|unset|default`, `ctxt profile schema add-*|remove-*`, `ctxt registry delete` and `ctxt watch enable|disable` change only the keys they are about. Before, they saved the whole merged config: other config files, `-c` overlays, `-c key=value`, environment variables and every built-in default landed in the file.
- **Formatting kept.** Comments, key order, quoting, flow lists and blank lines survive the edit.
- **Target file unchanged.** The last `-c <path>` when given, else the user file (`$CTXT_CONFIG` or `$XDG_CONFIG_HOME/contexthelp/ctxt.yaml`). `ctxt setup` always writes the user file.
- **`ctxt setup` updates instead of replacing.** It sets its storage, inbox and provider keys and keeps the rest of an existing file. The prompt now reads `update it?`.
- **Entries from another file are refused.** `profile rm`, `profile schema ...` and `registry delete` fail, naming the file they write, when the profile or registry comes from another config file (a project `.contexthelp/ctxt.yaml`, say). Before, they reported success and the other file kept winning.
- **Inline `default: true`.** `profile set` and `profile unset` drop a contradicting `default: true` from the profiles in the file they write. Left in place it made the config fail to load (two defaults) or undid the clear.

#### Server endpoint routing

- **Docs**: `dpkms job list` and `dpkms job cancel` work on the local store; the `--server-url` in the embeddings manual example was dropped.

#### Serve ports

- **One bind per listener.** `dpkms serve` binds the HTTP, gRPC and cookie-bridge listeners once, before the pidfile is written, and hands each to its server. Before, it checked a port, released it, and bound it again later, so two instances started together could both pick the cookie bridge's 9377 and one failed.
- **Operator ports are exact.** A port given with `--port` or `--grpc-port` is bound or serve exits non-zero (`HTTP port 8180: listen tcp ...: bind: address already in use`). Before, a busy port was silently swapped for a random one.
- **Config and env set the ports.** `server.port`, `server.grpc_port` and `server.cookie_bridge_port` in the config file, or `CH_SERVER_PORT`, `CH_GRPC_PORT` and `CH_COOKIE_BRIDGE_PORT`, set the listener ports. Before, serve ignored them and always started from the defaults. Precedence: flag, then env, then config file, then the default. A port set any of these ways is exact; `0` takes an OS-assigned port.
- **Config and env set the other serve settings.** `server.workers` / `DPKMS_WORKERS` and the new `server.dev`, `server.reminder_interval` and `steps.path` reach `dpkms serve`. Before, serve used the flag defaults (4 workers, 1m reminders, no dev CORS, `~/.config/contexthelp/steps`) whatever the config said. A `profile.default` or `CTXT_PROFILE` no longer brings up the interactive profile picker. A passed flag still wins.
- **Defaults fall back, visibly.** With no flag, env var or config key, a busy default (HTTP 8080, gRPC 9090, cookie bridge 9377) moves to a free port and serve prints `note: <listener> default port <N> is in use; bound <M> instead`. `dpkms ps` lists the ports in use.
- **Refused start holds nothing.** A start that fails on one listener releases the ports it had already bound.
- **Cookie bridge port.** `--cookie-bridge-port` sets the bridge's port like `--port` and `--grpc-port` do theirs: exact when passed, `0` for an OS-assigned port. A port-0 bind prints no `note:` line, since nothing fell back. Throwaway instances (tests, the 12fcc recorder) pass `--cookie-bridge-port 0` and stay off 9377. The browser extension still connects to 9377.

#### Serve failure and shutdown

- **One failure stops everything.** When a `dpkms serve` component fails (HTTP, gRPC, cookie bridge, worker pool, watcher, reminders, federation), serve logs `error: <component>: <cause>`, stops every other component, HTTP included, and exits non-zero. Before, the other components stopped but HTTP kept answering on its port, the cause was never printed, and the process never exited.
- **Signals always work.** SIGTERM, SIGINT and SIGHUP are handled for serve's whole lifetime, including after a failure. Before, once a component had failed, they were caught and ignored, and only SIGKILL ended the process.
- **Bounded shutdown.** Serve exits within `jobs.drain_timeout` (default 30s) of a signal or failure, even if a component does not stop; the exit is then non-zero and names the components still running. A second signal while stopping exits at once.

#### Route scopes and roles

- **Every route requires a scope.** Each `/api/v1` route and gRPC method declares one scope in `verb:resource` form (ADR-023), for example `read:objects`, `write:objects`, `delete:objects`, `process:inbox`, `admin:audit`. A valid token without the scope gets 403 with code `INSUFFICIENT_SCOPE`, a message naming the scope, and `WWW-Authenticate: Bearer error="insufficient_scope"`. gRPC answers `PERMISSION_DENIED` with the same message. A missing or invalid token is still 401.
- **Roles are fixed scope bundles.**
  - `admin`: every scope except the session-only `signout:ui`.
  - `writer`: every `read:*` and `write:*` scope. Meant for capture-only devices: no deletes, no inbox triage or discard, no registry sync, no admin routes.
  - `reader`: every `read:*` scope.
- **Roles are validated.** A static token needs at least one known role. An unknown role (a typo) or an empty list fails `ctxt config validate` and stops `dpkms serve` before it binds a port.
- **Admin skips the entity gate.** Entity reads by an `admin` principal (listing, show, backlinks, pull) ignore namespace entitlements and quotas and record no metering event. Every other principal is still gated and metered.
- **`GET /api/v1/whoami`** returns the caller's `principal`, `provider`, `roles` and `scopes`, and `via`: `token`, `session` (a web UI browser session, with its `session` id, kind and expiry) or `none`. A private instance answers `principal: local`, `via: none`, with every scope.
- **Unchanged**: private instances (no `server.auth`) need no token and grant every scope. `POST /api/v1/federation/push` now needs `write:objects` on top of its `federation.token` rule: on protected/public instances the federation token must be a static token with the `writer` or `admin` role. `/health`, `/healthz` and gRPC health stay open.
- **Web UI sessions use route scopes.** A browser session signed in with `ctxt ui open` holds its token's scopes intersected with a fixed web UI set: `read:objects`, `read:inbox`, `read:feeds`, `read:jobs`, `read:registries`, `read:system`, `delete:objects`, `write:jobs`, plus `signout:ui`, which only sessions hold. A `reader` token's session only reads; an `admin` token's gets that set and nothing more. Everything else (pipelines, steps, registry changes, watches, the audit log, federation, the MCP mount, login links, other writes) answers `403 INSUFFICIENT_SCOPE` naming the scope. To make that set expressible, five scopes split from coarser ones without changing any role's reach: `read:mcp` (the MCP mount, from `read:objects`), `read:pipelines` (pipeline and step reads) and `read:watches` (from `read:system`), `delete:aliases` and `delete:searches` (from `delete:objects`). `read:ui` (mint a login code) is a read scope, so every role holds it, and it is never in the web UI set, so a session never mints. `signout:ui` (end your own session) belongs to sessions only; no role, `admin` included, holds it, so a token calling `DELETE /api/v1/ui/session` gets `403 INSUFFICIENT_SCOPE`.
- **Action**: check each token's `roles` in `server.auth.static.tokens`. Tokens used for capture from a laptop or phone that only add content can move to `writer`; anything that deletes, triages the inbox or manages pipelines, steps, watches, registries or the audit log needs `admin`. Scope table: [config-and-permissions](../manual/reference/config-and-permissions.md#inbound-auth-roles-and-scopes).

#### Named endpoints

- **Named `server.urls` entries.** An entry takes an optional `name`: lowercase letters, digits and hyphens, not all digits, unique. `name: ""` and duplicates fail the config load.
- **One endpoint per command.** `status`, `log`, `upgrade status`, `feed`, every `import`, `capture` (incl. `--inbox`), `analyze` and bare `ctxt <content>`, `capture tabs`, `capture history` and `list --q` resolve exactly one endpoint: `--server`, then `--instance` / `CTXT_INSTANCE`, then the `ctxt instance use` selection, then the first `server.urls` entry, then `server.url`, then `http://127.0.0.1:8080`. Before, these commands ignored `--instance` and `CTXT_INSTANCE`.
- **No failover.** Other `server.urls` entries are reachable only by name or `--server`. `capture` no longer walks to the next entry after a refused connection or a 401/403: it exits 70 or 5. `analyze`, `capture tabs`, `capture history` and `list --q` no longer try the next entry either.
- **Names resolve** to a `server.urls` entry first, then to a running local dpkms by pidfile name or port (`http://127.0.0.1:<port>`, with the token of a `server.urls` entry at that URL, else `server.token`). An unknown name exits 70 and lists the configured names and running instances; so does a stale `ctxt instance use` selection (clear it with `ctxt instance use -`).
- **Exit codes** on these commands follow ADR-077: unreachable 70, 401/403 5, 404 3, 409 4, 400/422 2, 5xx 6.
- **`ctxt instance`**: `list` shows named endpoints and running local instances, with whether a token is attached; `use` accepts either; `current` prints the name, URL, the layer that chose it and whether a token is attached. Tokens are never printed.
- **Removed**: the 404 fallback from `POST /api/v1/pipelines/enqueue` to `/api/v1/analyze` in the source importers.
- **Not yet**: commands that open the database directly (`stats`, `find`, `show`, `list` without `--q`, ...) resolve `--instance` only to a running local instance and fail with "no running dpkms instance" for a remote name until they move onto the API.
- **Action**: if you list several `server.urls` entries for failover, name them and select one explicitly. Docs: [`ctxt instance`](../ctxt/api-cli.md#ctxt-instance).

#### `ctxt inbox` over the API

- **API only.** `ctxt inbox list`, `triage`, `discard` and `clear` call the dpkms instance the command resolves (`--server`, `--instance`, `CTXT_INSTANCE`, `ctxt instance use`, then config), local or remote. They no longer open the database: with nothing answering they exit 70 instead of reading or changing the local store.
- **New endpoints.** `GET /api/v1/inbox/queue` (`?pending=`, `failed=`, `raw=`, `limit=`, `offset=`) serves `inbox list --pending/--failed/--raw`. It needs `read:inbox` and rejects an unknown, repeated, empty or malformed parameter with 400 `INVALID_PARAM`. `POST /api/v1/inbox/clear` discards every inbox item and answers `{"cleared": N}`. It needs `process:inbox`. REST only: gRPC has no inbox methods.
- **Scopes.** Listing needs `read:inbox` (every role). Triage, discard and clear need `process:inbox`, which only `admin` holds: a `writer` or `reader` token exits 5 and changes nothing. An unknown item ID exits 3.
- **Triage and discard act on inbox items only.** `POST /api/v1/inbox/{id}/triage` and `/discard` answer 404 `NOT_FOUND` for any object whose status is not `inbox` (`active`, `discarded`, `raw`) as well as for an unknown ID, and change nothing. They used to accept any object ID and flip it to `active` or `discarded`, hiding it from default listings. `ctxt inbox triage` and `discard` exit 3 with `no inbox item <id>` and point at `ctxt inbox list`.
- **Confirmation unchanged.** `discard` and `clear` still need `--confirm-token`. `--confirm=yes` alone is refused, and the refusal prints the token.
- **Fixed.** `inbox list --before` / `--after` now filter (they were accepted and ignored), and a malformed value exits 2. `clear` now discards every inbox item: it used to stop at 10,000.
- **Action**: run `dpkms serve` (or select a remote instance) before `ctxt inbox`, and use an `admin` token to triage, discard or clear.

#### Upgrade banner from the API response

- **Header.** While an upgrade is in progress or has failed, dpkms sets `X-Dpkms-Upgrade` on every `/api/v1` response, as an RFC 8941 dictionary: `state=in_progress, bucket=reingest_selective, done=47, total=120, eta=32`. A failed run adds `error="…"` (printable ASCII, at most 256 bytes), an `embeddings_migrate` run adds `target="…"`, and a run with skipped objects adds `failed=N`. Idle instances send no header. Protected and public instances send it only to authenticated callers, the same as the upgrade field on `/healthz`.
- **Banner.** `ctxt` and the `dpkms` client commands (`healthcheck`, `pipeline`, `step`) print `ℹ ctxt: upgrading <bucket>; <done>/<total> objects (<pct>%); ETA <eta>s; details: ctxt upgrade status` (or the `✗ … upgrade failed` line) on stderr from the first response that carries the header, once per command. It shows the state of the instance the command calls, local or remote.
- **Removed.** Neither CLI reads `upgrade-state.json` next to the local pidfiles any more. `dpkms` commands that work on the local store (`job`, `backup`, `restore`, `housekeeping`, …) print no banner; check `dpkms healthcheck` or `ctxt upgrade status` for the upgrade state. The daemon and the local `ctxt upgrade run` still write the file, but nothing reads it.
- **Hidden.** `--quiet`, `--no-hints` or a stderr that is not a terminal (pipes, CI, agents) hides the banner. Commands that don't call the dpkms API never print it. `ctxt status`, `ctxt upgrade status` and `dpkms healthcheck` read `/healthz`, which carries no header; they show the upgrade state in their own output.

#### Enqueue without a local fallback

- **No local queue.** `ctxt analyze`, bare `ctxt` fed on stdin or the clipboard, `ctxt capture tabs` and `ctxt capture history` send only to the one instance ctxt resolves. When nothing answers there they exit 70 (`PREREQUISITE`); when it answers 401 or 403 they exit 5 (`UNAUTHORIZED`) and the request is not retried. Before, both cases enqueued into a local `db.sqlite` and printed `Queued locally; the job will run when the daemon starts`, and a remote daemon never saw those jobs.
- **Removed**: the `Queued locally` message, the `queued_locally` field of the `capture tabs` / `capture history` JSON, the `(queued locally)` note in their listings, and the CLI's database lock on that path.
- **Batches stop on the first 70 or 5.** `capture tabs` and `capture history` print their report, then exit with that code. The URLs they never attempted show as `not sent N` in the summary and `would_send` in the JSON. Other failures (a 5xx, a refused URL) are still recorded per URL, and the run goes on and exits 1.
- **`analyze` errors follow ADR-077**: a request the instance refuses (a 422 for an unrouted type or pipeline) exits 2 instead of 1, with the instance's message; a 5xx exits 6.
- **History position per instance.** The position file keys each browser profile by instance: the `server.urls` entry's name, else its URL. Capturing into one instance, then another, sends the full window to the second. The file is now version 2. A version-1 file stops `capture history` with exit 3 (`unsupported position file version: version 1`) and is never converted or rewritten; `--reset-position` can't read it either. The JSON `position` block gains `instance`, and `--reset-position` resets the resolved instance only.
- **Unchanged**: `ctxt capture [source]` already exited 70 or 5. `list --q` lost its local search separately (see "`list --q` searches the instance only").
- **Action**:
  - Delete the position file once: `browserhistory.state` under `$XDG_STATE_HOME/ctxt/ambient/` (see [Saved position](../manual/workflows/browser-history-capture.md#saved-position); `ctxt capture history -V` prints the path). The next plain run per browser profile reads back `capture.history.initial_lookback`; pages the instance already has are deduplicated.
  - Scheduled captures (`ctxt capture schedule`) and scripts now fail while the instance is down: check their exit status.
  - A local `db.sqlite` left by earlier fallbacks is read by nothing. Capture its content again if you need it.

#### Edit, delete and reprocess over the API

- **One path.** `ctxt edit`, `ctxt delete` and `ctxt reprocess` call the dpkms API and never open a local database. They follow `--server`, `--instance`, `CTXT_INSTANCE` and `ctxt instance use` like every other API command, so they work against a remote dpkms. Exit codes follow ADR-077: unreachable 70, 401/403 5, unknown object 3, bad input 2.
- **`ctxt edit`** sends `PATCH /api/v1/objects/{id}` (`write:objects`: `writer` or `admin`). The endpoint now takes `title`, `summary`, `tags` and `mentions` besides `type` and `subtype`. `--title` and `--summary` both set the first summary, so combining them is now an error (exit 2). Before, `--summary` silently overwrote `--title`.
- **`ctxt delete`** lists its matches with `GET /api/v1/objects` and deletes each with `DELETE /api/v1/objects/{id}` (`delete:objects`, admin only).
  - A `writer` token exits 5 and deletes nothing; the run stops at the first refused request.
  - `--dry-run` and `--confirm=no` name exactly the objects a committed run deletes, and need only a read token. kit's `--confirm` / `--confirm-token` gate is unchanged.
  - A filter now deletes every match. Before, `--tagged`, `--mention` and `--type` stopped at 1,000 objects and `--all` at 10,000, while the count printed was the full total.
  - A filter still selects active objects only.
  - A failed delete other than a refusal makes the command exit non-zero after the others have run. Before, it exited 0 with a warning.
- **`ctxt reprocess`** sends `POST /api/v1/objects/{id}/reprocess` (`write:objects`) and prints the job ID. `--format json` prints `{id, step, job_id, status: "queued"}`.
  - The step runs on the dpkms host as an `object:reprocess` job, with that host's LLM provider and configuration. Before, it ran in the ctxt process with the laptop's providers.
  - The hyphenated `structured-metadata` spelling is gone.
  - Follow the job with `GET /api/v1/jobs/{id}`; `result_id` is the object ID once it completes.
- **Removed flags**, which were bound but never applied: `edit --hints`, `edit --decisions`, `delete --index`, `delete --hint`, `delete --subtype`.
- **API**: `PATCH /api/v1/objects/{id}` rejects unknown fields, a body with no field, and `title` together with `summary` (400 `INVALID_REQUEST`), and bad mentions (400 `INVALID_MENTION`). `PATCH` and `DELETE` return 500 rather than 404 when storage fails. None of the three routes has a gRPC method. Docs: [api-rest](../api/api-rest.md#patch-objectsid), [`ctxt delete`](../ctxt/api-cli.md#ctxt-delete).
- **Action**: use an `admin` token for `ctxt delete`. Drop the removed flags from scripts, and spell the reprocess step `structured_metadata`.

#### `ctxt link` over the API

- **API only.** `ctxt link create`, `list` and `delete` call the dpkms instance the command resolves (`--server`, `--instance`, `CTXT_INSTANCE`, `ctxt instance use`, then config) and never open a local database. Exit codes follow ADR-077: unreachable 70, 401/403 5, unknown object 3, unknown link type 2 (both exited 1 before).
- **New endpoints.** `POST /api/v1/edges` stores a link and its inverse (`write:objects`). `GET /api/v1/objects/{id}/edges` lists an object's edges, or walks its links with `depth=1..3` (`read:objects`). `DELETE /api/v1/edges?source=&target=&type=` removes the links between two objects in both directions and answers `{"deleted": N}`. REST only: gRPC has no edge methods. Docs: [api-rest](../api/api-rest.md#post-edges).
- **Link and inverse together.** dpkms writes a link and its inverse (`extends` and `extended-by`) in one transaction, and deletes them in one. Before, the CLI wrote them one at a time, so a failure between the two left a half link.
- **New scope `delete:edges`.** Only `admin` holds it: a `writer` token creates links but its `link delete` exits 5 and removes nothing. It is split from `delete:objects`, which a web UI browser session holds, so a session can read links (`read:objects`) but never create or delete them.
- **Unchanged output.** `link list`, with or without `--follow`, prints what it printed before; `--follow` above 3 still walks 3 hops.
- **`link list` on an unknown object** exits 3 with `object not found` instead of printing `No links found.`
- **Action**: run `dpkms serve` (or select an instance) before `ctxt link`, and use an `admin` token for `link delete`.

#### `ctxt find` over the API

- **One path.** `ctxt find` sends `POST /api/v1/find` (`read:objects`, every role) to the instance `--server`, `--instance`, `CTXT_INSTANCE` or `ctxt instance use` selects, local or remote, and never opens a database. `ctxt://search/<query>` and a REPL line that falls through to `find` run the same request. `find --graph` still searches the local store for now.
- **Settings travel with the query.** ctxt resolves the search strategy (global `search`, the active profile's `search_strategy`, then the flags) and sends every knob: `rrf_k`, the weights and pools, `min_score`, `fallback_to_fts` and the reranker weights. dpkms applies what arrives.
- **Profile scope (new).** The active profile, from `--profile` or `profile.default`, is sent as `profile`, and dpkms answers only objects captured under it, in every mode and in `--facets` counts. Before, the profile only picked the search strategy and `find` searched every object.
- **Query embedding on the dpkms host.** dpkms embeds the query with its default model and the provider settings where `dpkms serve` runs. The `--embedding-provider`, `--embedding-model` and `--embedding-endpoint` flags now apply to `--graph` only; without it they exit 2 before any request. To reach the model through a tunnel, set `CTXT_EMBEDDING_ENDPOINT` for `dpkms serve`.
- **Output.** `--format json` keeps its shapes: `objects`, `total`, `query`, `mode`, `diagnostics` (plus `facets`), and `results[]` of `object`, `score_breakdown`, `document_view` with `--explain`. Explain results carry no `metadata.rrf_score`, as before; plain hybrid results still do. Empty results are `[]`, as before.
- **Removed.** The "Did you mean" hints after an empty result. REPL session-context blending: a REPL query is no longer biased toward the previous queries' vectors.
- **Changed.**
  - The human `--facets` block lists types in sorted order.
  - A malformed `--since` or `--until` exits 2 (dpkms answers 400). Before, the filter was silently dropped.
  - With `search.fallback_to_fts: false`, a semantic leg that cannot run exits 2 (422 `SEMANTIC_UNAVAILABLE`, naming the status and model) instead of a generic failure.
  - A facet count failure exits 6 (dpkms answers 500). Before, `find` printed the results without facets.
  - An unknown `search.default_mode` or profile `search_strategy.mode` exits 2.
- **Fixed.** `ctxt ctxt://search/<query>` (and `ctxt ctxt://<id>`) ran into the root command's unknown-command check and exited 2; the root now accepts one `ctxt://` operand.
- **Exit codes** follow ADR-077: unreachable 70, 401/403 5, 400/422 2, 5xx 6.
- **Action**: start `dpkms serve` or select an instance before `ctxt find`. If `profile.default` is set and you want every object, unset it. Drop `--embedding-*` from `find` scripts and set the provider where dpkms runs. Docs: [`ctxt find`](../ctxt/api-cli.md#ctxt-find), [Turn on semantic search](../manual/workflows/semantic-search.md).

#### Entity pages, topic index and stats over the API

- **One path.** `ctxt page list|show|refresh`, `ctxt index [topic] [--refresh]` and `ctxt stats [--watch]` call the dpkms API and never open a local database. They follow `--server`, `--instance`, `CTXT_INSTANCE` and `ctxt instance use`, so they work against a remote dpkms. Exit codes follow ADR-077: unreachable 70, 401/403 5, unknown page 3.
- **Scopes.** Reads need `read:objects`, so a `reader` token and a browser session can make them. `ctxt page refresh` (`POST /api/v1/pages/{slug}/refresh`) and `ctxt index --refresh` (`POST /api/v1/topic-index`) need `write:objects`; a `reader` exits 5.
- **`ctxt index`** before the first rebuild exits 3 and suggests `ctxt index --refresh`. Before, it printed a hint and exited 0. `ctxt index <topic> --format json` now prints `[]` for a topic without entries.
- **`ctxt stats`** is counted on the server (`GET /api/v1/stats`); it no longer lists every object to count types. Profiles stay this client's configuration; the resurfacing count is the default profile's, no longer capped at 1,000. On a gated instance `entities` counts only the entities the token may list. On Postgres, which has no resurfacing queue yet, `resurfacing_candidates` is `null` and the text output prints `-`.
- **`ctxt stats --watch`** fails on its first snapshot like a plain `ctxt stats`. Before, it printed the error and kept polling forever.
- **API**: new routes, REST only. Docs: [api-rest](../api/api-rest.md#entity-pages-topic-index-and-stats), [`ctxt page`](../ctxt/api-cli.md#ctxt-page), [`ctxt index`](../ctxt/api-cli.md#ctxt-index), [`ctxt stats`](../ctxt/api-cli.md#ctxt-stats).
- **Action**: start `dpkms serve` or select an instance before using these commands, and use a `writer` or `admin` token to refresh pages or rebuild the index.

#### `list --q` searches the instance only

- **No local search.** `ctxt list --q "<rsql>"` calls `GET /api/v1/search` on the instance ctxt resolves (`--server`, `--instance`, `CTXT_INSTANCE`, `ctxt instance use`, then config). It no longer opens the local store first, and a refused token no longer falls back to searching the local corpus.
- **Exit codes** follow ADR-077: unreachable 70, 401/403 5, a malformed query 2.
- **Removed**: the `internal/idxbridge` package (health probe, probe cache, local search fallback). The `dpkms` client commands (`healthcheck`, `pipeline`, `step`) take their endpoint type and `http://127.0.0.1:8080` default from the ctxt client package instead; their behaviour is unchanged.
- **Action**: start `dpkms serve` or select an instance before `ctxt list --q`.

#### Object reads over the API

- **One path.** `ctxt list` (filters, `--facets`, `--cursor`), `ctxt show`, `ctxt export`, `ctxt classify o-…`, `ctxt compose` and `ctxt profile schema evolve` read from the instance ctxt resolves (`--server`, `--instance`, `CTXT_INSTANCE`, `ctxt instance use`, then config) and never open a local database. Exit codes follow ADR-077: unreachable 70, 401/403 5, unknown object 3, bad input 2.
- **Routes**, all `read:objects`: `GET /api/v1/objects` for list, compose and schema evolve; `GET /api/v1/objects/facets` for `list --facets`; `GET /api/v1/objects/{id}` and `/related` for show; `GET /api/v1/objects/{id}` for export and classify.
- **Client-side work.** Composition, classification and the schema-evolution analysis run in the ctxt process on the objects read. The `list --cursor` position stays a local file.
- **`ctxt list`**
  - `--tagged` takes one tag; several exit 2. Match several with `--q "tag=in=(a,b)"`. Before, `--tagged a,b` matched only a tag literally named `a,b`.
  - `--sort` takes `created` (default; `recent` is a synonym) or `updated`, which now sorts by update time. `view`, `match`, `weight` and `score` exit 2; before, every key sorted by creation time.
  - `--after` and `--before` take `YYYY-MM-DD` or RFC 3339, `--since` and `--until` `YYYY-MM-DD`. A malformed value exits 2; before, it was silently ignored.
  - `--facets` prints the metadata types sorted.
- **`ctxt compose`**: `--since` and `--until` bound creation time and take `YYYY-MM-DD` or RFC 3339. Natural-language values (`yesterday`, `now`) were never applied and now exit 2. `--tagged` takes one tag. An unknown type or `--export` value exits 2.
- **`ctxt show`** and **`ctxt export`**: the output-generator plugin branches are gone (no plugin could reach them). `export` prints JSON, or YAML with `--format yaml`.
- **Removed flags**, which were bound but never applied: `list --hint`, `list --orig-lang`, `list --no-track`, `export --dest`, `compose --session`.
- **Action**: start `dpkms serve` or select an instance before these commands. Drop the removed flags from scripts, split multi-tag `--tagged` filters into `--q`, and spell dates as `YYYY-MM-DD` or RFC 3339. Docs: [`ctxt list`](../ctxt/api-cli.md#ctxt-list), [`ctxt compose`](../ctxt/api-cli.md#ctxt-compose).

#### Blob store wired into every storage driver

- **What was lost.** The SQLite and Postgres drivers started with a no-op blob store, and only `dpkms backup` read `storage.blob`. A pipeline step that moves content above `storage.blob.threshold` (default 64 KiB) into the blob store stored `blob://<key>` in the object and dropped the content. No built-in pipeline runs that step (`externalize_content`), so only pipelines that add it (`pipelines.<name>.extra_steps`) lost content.
- **Now.** `dpkms serve` and every command that opens the store build the driver with the `storage.blob` store. A driver can't be built without one. `storage.blob.backend: stub` and `local` with an empty `local.path` stop the command at startup.
- **Check for earlier loss**: objects with `raw_content LIKE 'blob://%'` whose key has no file under `storage.blob.local.path` (`<key[0:2]>/<key[2:4]>/<key>`). Their content may still be in the ingest job's payload (`jobs.payload`) until job history is pruned (30 days), or at the source: re-ingest from there.
- **Action**: none for a default install. Make sure the disk under the data directory, or `storage.blob.local.path`, has room for large content.

#### Blob refs resolved on read

- **Before.** Nothing read the blob store back: `GET /objects/{id}`, lists, `/search`, `POST /find`, gRPC, the MCP `search` tool and `ctxt show`/`export` returned `raw_content: "blob://<key>"` (and `text_content`, which defaults to it) for content above `storage.blob.threshold`. Re-analysis ran its pipeline on that ref string.
- **Now.** The service resolves refs on every object read. `GET /objects/{id}` and `PATCH` return the whole content. Lists and searches return at most `storage.blob.threshold` bytes (the most an inline object holds), with `metadata.content_truncated: true` when cut; `metadata.blob_original_size` is the full length. A missing or unreadable blob fails the request (500) instead of answering the ref.
- **Writes.** An update writes content above the threshold to the blob store, and a list preview written back keeps the stored content, so read-modify-write never inlines or truncates it. Re-analysis does the same whether or not its pipeline has `externalize_content`.
- **Action**: none. API clients that resolved `blob://` refs themselves can drop that code; read an object by ID when `metadata.content_truncated` is set.

#### Restore writes blobs into the blob store

- **Before.** `dpkms restore` wrote each backed-up blob to `<dir of storage.path>/blobs/<key>`: not `storage.blob.local.path` when that is set, and not the store's `<key[0:2]>/<key[2:4]>/<key>` layout, so a restored object's `blob://` ref never resolved.
- **Now.** Each blob goes through the configured store's own write, wherever and however that store keeps it. A blob entry that is not a bare key is refused. `--dry-run` opens no store.
- **Action**: if you restored a backup made with `--include-blobs`, restore it again; delete the stray `blobs/` directory beside the database if it is not your `storage.blob.local.path`.
- **Metadata.** Each blob's `BlobMeta` (content type, filename, content hash, properties) is archived as `blobmeta/<key>.json`, before `blobs/<key>`, and restored through the same `Put`; size comes from the blob itself. A blob without a sidecar restores with size only, as every blob did before.

#### Restore keeps every entry inside its target

- **Before.** `dpkms restore` joined each `config/<path>` entry onto the config dir as given, so `config/../../x` or an absolute path wrote outside it. A tar symlink, hard link or device entry was written as an empty regular file (a `ctxt.db` one truncated the database), and a directory backup's symlinks were followed, copying the file they pointed at. The manifest's schema check ran after every entry was written, and a directory backup's manifest was never read. `ctxt config restore` joined bundle entry names onto the config dir the same way.
- **Now.** A first pass reads the whole archive or directory and refuses it, with nothing written, when any entry restore would write is not a regular file, a config entry is not a plain relative path, a blob entry is not a bare key, or the manifest is unsupported. It also stops before writing when the backup holds config files and no config dir is set, or blobs and no blob store. Config files are written through an `os.Root` on the config dir, so a symlink already in it cannot lead outside either. `ctxt config restore` applies the same name and file-type rules to bundle entries and creates their parent directories.
- **Action**: none. A refused backup was not made by `dpkms backup`: check where it came from.

#### Restore writes the config file back; atomic database replace

- **Before.** `dpkms backup` always archives the config file it runs with (`--config`, `CTXT_CONFIG`, else `contexthelp/dpkms.yaml`) as `config.yaml`, but `dpkms restore` never wrote it back, though its help said configs were restored. The database was truncated and rewritten in place: a restore that failed part-way left a truncated database, and an old `-wal` beside it could be replayed onto the restored file. A running `dpkms serve` kept writing to the database under the restore.
- **Now.** `config.yaml` restores, verbatim, to the config file the restore resolves, under that file's own name, through the same `os.Root` rules as `config/` entries; `--skip-configs` skips it with them. The database goes to a temporary file beside `storage.path`, is fsynced, renamed over it, the old `-wal`, `-shm` and `-journal` files are removed and the directory is fsynced. Restore, `--dry-run` included, refuses while a live pidfile in the data dir's `run/` records that database (a relative recorded path counts as a match).
- **Action**: stop the instance (`dpkms shutdown`) before restoring. If you restored a backup before this release and needed its config, restore it again or copy `config.yaml` out of the archive.

#### Serve holds the database lock

- **Before.** The only sign that a `dpkms serve` was running on a database was its pidfile, written best effort after the listeners were bound. Two serves could run on one SQLite database, and `dpkms restore` replaced a database under a serve whose pidfile was missing or in another data dir's `run/`.
- **Now.** `dpkms serve` takes an advisory `flock` on `<storage.path>.lock` before it opens the database and holds it until it exits (the kernel drops it if the process dies). A second serve on that database exits before opening it, naming the holder's pid and instance. `dpkms restore` refuses, `--dry-run` included, while the lock is held, on top of the pidfile check, and holds the lock itself while it replaces the database. Postgres and in-memory databases take no lock. Other commands that open the database (`housekeeping`, `backup`, the `ctxt` direct-store path) go through SQLite's own locking and do not take it.
- **Action**: none. Run one serve per database; leave the `.lock` file in place.

#### Federation push carries blob content

- **Before.** Federation copied rows only. An object whose content was externalized reached the target as a `blob://<key>` ref with no blob behind it: a local target looked for it in its own store, a remote receiver stored the literal ref.
- **Local push** (`file://` or path targets). The blob goes into the target's blob store before the row is written: the entry's `blob` setting (same keys as `storage.blob`) when set, else `blobs/` beside the target database, the default `storage.blob.local.path` of a data dir holding it. Point `blob` at the target instance's own `storage.blob` when it keeps its blobs elsewhere (`storage.blob.local.path` set, or `s3`/`garage`).
- **Remote push** (`http(s)://` targets). `POST /api/v1/federation/push` has no blob channel, so the pusher sends the content inline. The receiver stores content above its own `storage.blob.threshold` in its own blob store.
- **Failure.** A ref whose blob is missing at the source fails the batch: nothing after it lands and the watermark stays, so the next tick retries. After 3 ticks in a row failing on the same object it is skipped and logged (`federation: skipping object after repeated push failures`); the rest of the batch goes through and the watermark moves past it. Editing the object, once its blob is back, pushes it again. A source store that cannot be read (network, timeout, S3 5xx or access denied) fails the tick too but never counts toward the skip.
- **Action**: objects pushed before this release keep their dangling refs at the target. Delete them there and push again, or re-ingest at the target.

#### Federation pushes only changes

- **Before.** Every `async` tick listed every source object, with its edges, and pushed them all; the receiver skipped what it already had. A remote push sent every object's content inline on every tick. The watermark was written after each push but never read.
- **Now.** The store stamps every object insert and update with the next change sequence (`objects.change_seq`), whatever `updated_at` the writer set, and the values commit in order. The watermark is the change sequence of the last object the target acknowledged. A local target keeps it in its own database, a remote one in the source's, both under the federation `name`. A tick lists the objects after it, in change-sequence order, and pushes them 100 per batch; a remote batch goes out in requests of at most 4 MiB of encoded objects (an object larger than that goes alone; the receiving dpkms reads a body up to its `federation.max_request_bytes`, 256 MiB by default, and an object it or a proxy in front refuses with 413 is skipped after 3 ticks, like a missing blob). The watermark moves after each acknowledged batch or request, so a refused one is re-sent next tick and nothing before it is. Imports, restores and objects a receiver forwards to its own targets are pushed like any other write.
- **Unchanged.** Edges and entities travel with the objects they belong to. Receivers still skip objects whose content hash or id they hold, so an edited object is re-sent but not updated at the target, and deletes are not propagated.
- **Action**: none. Renaming a federation entry, or replacing a local target's database, starts its watermark over: the next tick pushes everything once.

#### Snapshot before schema migrations

- **Before.** A new binary applied pending schema migrations on its first open with no copy of the database: a migration that failed half-way or did the wrong thing could not be undone.
- **SQLite.** Before the first pending migration runs on an existing database, the open writes a consistent copy (`VACUUM INTO`, fsynced, mode `0600`) to `backups/pre-migrate-v<from>-v<to>-<UTC time>.sqlite` beside the database file. No copy when the schema is current or the database is new. If the copy fails, the open fails and the database keeps its old version.
- **Retention.** The newest 3 `pre-migrate-*` snapshots per `backups/` directory are kept; older ones are deleted only after a new one is written. Each is about the size of the database.
- **Not copied.** Blobs (content-addressed, never changed by migrations) and Postgres databases. On Postgres a warning names the from/to versions and recommends `pg_dump`; the migration still runs.
- **Opt out.** `storage.migrate_snapshot: false`.
- **Preview.** `ctxt upgrade plan` with the new binary reports the pending versions and the snapshot directory without migrating.
- **Action**: none. Rollback steps: [runbook](../manual/operations/runbook.md#schema-migrations-snapshot-the-database-first).
