## Changes by bucket

### `reindex_auto` changes

#### Re-projection on a projection change

- **What changed**
  - Each object records the projection version its full-text body was built with (`objects.projection_version`). Ingest and updates stamp the current version.
  - When the `objects_fts` signature doesn't match on startup, `dpkms serve` queues a background job (`projection:reproject`). It rebuilds each stale object's full-text body and index entry from the stored object, then stamps the signature. It does not re-run pipelines or call a provider.
  - Startup no longer stamps a mismatched signature. The mismatch stays until the job has re-projected every object, so a run cut short is picked up again on the next start.
  - Progress: `ctxt upgrade status` shows bucket `reindex_auto` with target `projection@v2`, `done`/`total`, and `failed`. Bus events are `dpkms.upgrade.reprojection.{scheduled,started,progressed,completed,failed}`.
- **Signature bump**: migration 040 (Postgres 18) clears the stored `objects_fts` hash. Rows written before it carry no stamp, and databases that ran the 2026-09-26 release had already stamped the `v2` signature over bodies built by `v1`. On the first start after this release, every object is re-projected once. That run applies the repeated-segment fix from 2026-09-26 to stored objects.
- **Estimated wall-clock**: one short transaction per object and no model calls, so it runs at local write speed. Not measured on a large corpus; expect it to scale with object count. Search keeps serving: each object switches to its new text as it is reached.
- **Resume and failures**:
  - A run stopped by shutdown, crash or `dpkms job cancel` resumes on the next start with the objects not yet done. Finished objects are not redone.
  - An object that can't be re-projected is counted, left with its old text, and retried on the next start. `ctxt upgrade status` stays `failed`, with `last_error` naming the first failure.
- **Not refreshed: embeddings.** Stored vectors keep the text they were embedded from, including the doubled segments from before 2026-09-26. This job doesn't re-embed.
- **Concurrent work**: ingest during the run is safe. New and updated objects are written with the current projection and skipped by the job. While an embedding migration holds the upgrade status, the re-projection waits for it to finish.

### `none` changes

#### Search on dpkms

- **MCP**: the `search` tool runs `POST /api/v1/find`'s search, `hybrid` by default. It takes `mode` (`hybrid`, `fts`, `vector`), `profile`, `min_score` (hybrid only) and the facet filters (`since`/`until` as `YYYY-MM-DD`), and returns titles, snippets and scores. Its description no longer claims hybrid while running RSQL.
- **No embedding model or provider**: the tool answers from full text and says so (`executed_mode` `fts_only` or `fts_fallback`, `diagnostics.semantic`).
- **Profiles**: full-text, vector and hybrid search now honor a profile on SQLite and Postgres. `POST /api/v1/find` and the MCP tool take `profile`; leaving it out searches every profile. Postgres now stores each object's profile. The caller chooses the profile; it is not an access control.

#### Search graph on dpkms

- **REST**: `GET /api/v1/search/graph` returns the hybrid search trace as a JGF document (`ctxt.search-graph/v1`), the one `ctxt find --graph --format json` prints. Parameters: `q`, `profile`, `limit` (default 10), `min_score`, `POST /api/v1/find`'s filters, `max_nodes` (default 250, at most 1000), `max_edges` (default 1500, at most 10000), `similar`, `similar_threshold`. The body is the bare document, not `{data, total}`. See [api-rest.md](../api/api-rest.md#get-searchgraph).
- **Entitlements**: entities in namespaces the caller is not entitled to are left out entirely, including from `co_mention` weights and counts. Not metered, like search.
- **No embedding model or provider**: `200` with a full-text-only graph (`metadata.mode` `fts_only` or `fts_fallback`).
- **Web UI**: `/ui/searchgraph/?q=<query>` shows the graph in the viewer `ctxt find --graph` opens. The page's query string goes to `GET /api/v1/search/graph` unchanged; a click on an object links to `/ui/objects/<id>`. `/ui/searchgraph` redirects there with the query kept. Same headers as the rest of `/ui` (no framing, `nosniff`, `no-referrer`), plus the page's own Content-Security-Policy: same-origin scripts, styles and requests only. Works on private instances and behind a reverse proxy that signs you in; instances that check tokens themselves refuse the graph request (`401`) until the web UI can sign in. See [search-graph.md](../manual/workflows/search-graph.md#open-it-in-the-web-ui).

#### Config write commands

- **Only the edit is written.** `ctxt setup`, `ctxt profile create|rm|set|unset|default`, `ctxt profile schema add-*|remove-*`, `ctxt registry delete` and `ctxt watch enable|disable` change only the keys they are about. Before, they saved the whole merged config: other config files, `-c` overlays, `-c key=value`, environment variables and every built-in default landed in the file.
- **Formatting kept.** Comments, key order, quoting, flow lists and blank lines survive the edit.
- **Target file unchanged.** The last `-c <path>` when given, else the user file (`$CTXT_CONFIG` or `$XDG_CONFIG_HOME/contexthelp/ctxt.yaml`). `ctxt setup` always writes the user file.
- **`ctxt setup` updates instead of replacing.** It sets its storage, inbox and provider keys and keeps the rest of an existing file. The prompt now reads `update it?`.
- **Entries from another file are refused.** `profile rm`, `profile schema ...` and `registry delete` fail, naming the file they write, when the profile or registry comes from another config file (a project `.contexthelp/ctxt.yaml`, say). Before, they reported success and the other file kept winning.
- **Inline `default: true`.** `profile set` and `profile unset` drop a contradicting `default: true` from the profiles in the file they write. Left in place it made the config fail to load (two defaults) or undid the clear.

#### Server endpoint routing

- **Server routing, ctxt**: `feed add|list|sync|delete`, `import batch`, `import batch status`, `import email` and the source importers (`chrome`, `discord`, `dropbox`, `edge`, `evernote`, `firefox`, `gdrive`, `github`, `linkedin`, `logseq`, `notion`, `obsidian`, `onedrive`, `pinboard`, `raindrop`, `safari`, `slack`, `twitter`) resolve the server the same way as `status` and `log`: `--server`, then the `server.urls` primary, then `server.url` (config file or `-c`), then `http://127.0.0.1:8080`. - **Docs**: `dpkms job list` and `dpkms job cancel` work on the local store; the `--server-url` in the embeddings manual example was dropped.

#### Serve ports

- **One bind per listener.** `dpkms serve` binds the HTTP, gRPC and cookie-bridge listeners once, before the pidfile is written, and hands each to its server. Before, it checked a port, released it, and bound it again later, so two instances started together could both pick the cookie bridge's 9377 and one failed.
- **Operator ports are exact.** A port given with `--port` or `--grpc-port` is bound or serve exits non-zero (`HTTP port 8180: listen tcp ...: bind: address already in use`). Before, a busy port was silently swapped for a random one.
- **Defaults fall back, visibly.** A busy default (HTTP 8080, gRPC 9090, cookie bridge 9377) moves to a free port and serve prints `note: <listener> default port <N> is in use; bound <M> instead`. `dpkms ps` lists the ports in use.
- **Refused start holds nothing.** A start that fails on one listener releases the ports it had already bound.

#### Serve failure and shutdown

- **One failure stops everything.** When a `dpkms serve` component fails (HTTP, gRPC, cookie bridge, worker pool, watcher, reminders, federation), serve logs `error: <component>: <cause>`, stops every other component, HTTP included, and exits non-zero. Before, the other components stopped but HTTP kept answering on its port, the cause was never printed, and the process never exited.
- **Signals always work.** SIGTERM, SIGINT and SIGHUP are handled for serve's whole lifetime, including after a failure. Before, once a component had failed, they were caught and ignored, and only SIGKILL ended the process.
- **Bounded shutdown.** Serve exits within `jobs.drain_timeout` (default 30s) of a signal or failure, even if a component does not stop; the exit is then non-zero and names the components still running. A second signal while stopping exits at once.

#### Route scopes and roles

- **Every route requires a scope.** Each `/api/v1` route and gRPC method declares one scope in `verb:resource` form (ADR-023), for example `read:objects`, `write:objects`, `delete:objects`, `process:inbox`, `admin:audit`. A valid token without the scope gets 403 with code `INSUFFICIENT_SCOPE`, a message naming the scope, and `WWW-Authenticate: Bearer error="insufficient_scope"`. gRPC answers `PERMISSION_DENIED` with the same message. A missing or invalid token is still 401.
- **Roles are fixed scope bundles.**
  - `admin`: every scope except the session-only `signout:ui`.
  - `writer`: every `read:*` and `write:*` scope. Meant for capture-only devices: no deletes, no inbox triage or discard, no registry sync, no admin routes.
  - `reader`: every `read:*` scope.
- **Roles are validated.** A static token needs at least one known role. An unknown role (a typo) or an empty list fails `ctxt config validate` and stops `dpkms serve` before it binds a port.
- **Admin skips the entity gate.** Entity reads by an `admin` principal (listing, show, backlinks, pull) ignore namespace entitlements and quotas and record no metering event. Every other principal is still gated and metered.
- **`GET /api/v1/whoami`** returns the caller's `principal`, `provider`, `roles` and `scopes`, and `via`: `token`, `session` (a web UI browser session, with its `session` id, kind and expiry) or `none`. A private instance answers `principal: local`, `via: none`, with every scope.
- **Unchanged**: private instances (no `server.auth`) need no token and grant every scope. `POST /api/v1/federation/push` now needs `write:objects` on top of its `federation.token` rule: on protected/public instances the federation token must be a static token with the `writer` or `admin` role. `/health`, `/healthz` and gRPC health stay open.
- **Web UI sessions use route scopes.** A browser session signed in with `ctxt ui open` holds its token's scopes intersected with a fixed web UI set: `read:objects`, `read:inbox`, `read:feeds`, `read:jobs`, `read:registries`, `read:system`, `delete:objects`, `write:jobs`, plus `signout:ui`, which only sessions hold. A `reader` token's session only reads; an `admin` token's gets that set and nothing more. Everything else (pipelines, steps, registry changes, watches, the audit log, federation, the MCP mount, login links, other writes) answers `403 INSUFFICIENT_SCOPE` naming the scope. To make that set expressible, five scopes split from coarser ones without changing any role's reach: `read:mcp` (the MCP mount, from `read:objects`), `read:pipelines` (pipeline and step reads) and `read:watches` (from `read:system`), `delete:aliases` and `delete:searches` (from `delete:objects`). `read:ui` (mint a login code) is a read scope, so every role holds it, and it is never in the web UI set, so a session never mints. `signout:ui` (end your own session) belongs to sessions only; no role, `admin` included, holds it, so a token calling `DELETE /api/v1/ui/session` gets `403 INSUFFICIENT_SCOPE`.
- **Action**: check each token's `roles` in `server.auth.static.tokens`. Tokens used for capture from a laptop or phone that only add content can move to `writer`; anything that deletes, triages the inbox or manages pipelines, steps, watches, registries or the audit log needs `admin`. Scope table: [config-and-permissions](../manual/reference/config-and-permissions.md#inbound-auth-roles-and-scopes).

#### Named endpoints

- **Named `server.urls` entries.** An entry takes an optional `name`: lowercase letters, digits and hyphens, not all digits, unique. `name: ""` and duplicates fail the config load.
- **One endpoint per command.** `status`, `log`, `upgrade status`, `feed`, every `import`, `capture` (incl. `--inbox`), `analyze` and bare `ctxt <content>`, `capture tabs`, `capture history` and `list --q` resolve exactly one endpoint: `--server`, then `--instance` / `CTXT_INSTANCE`, then the `ctxt instance use` selection, then the first `server.urls` entry, then `server.url`, then `http://127.0.0.1:8080`. Before, these commands ignored `--instance` and `CTXT_INSTANCE`.
- **No failover.** Other `server.urls` entries are reachable only by name or `--server`. `capture` no longer walks to the next entry after a refused connection or a 401/403: it exits 70 or 5. `analyze`, `capture tabs`, `capture history` and `list --q` no longer try the next entry either; their local fallback is unchanged for now.
- **Names resolve** to a `server.urls` entry first, then to a running local dpkms by pidfile name or port (`http://127.0.0.1:<port>`, with the token of a `server.urls` entry at that URL, else `server.token`). An unknown name exits 70 and lists the configured names and running instances; so does a stale `ctxt instance use` selection (clear it with `ctxt instance use -`).
- **Exit codes** on these commands follow ADR-077: unreachable 70, 401/403 5, 404 3, 409 4, 400/422 2, 5xx 6.
- **`ctxt instance`**: `list` shows named endpoints and running local instances, with whether a token is attached; `use` accepts either; `current` prints the name, URL, the layer that chose it and whether a token is attached. Tokens are never printed.
- **Removed**: the 404 fallback from `POST /api/v1/pipelines/enqueue` to `/api/v1/analyze` in the source importers.
- **Not yet**: commands that open the database directly (`stats`, `find`, `show`, `list` without `--q`, ...) resolve `--instance` only to a running local instance and fail with "no running dpkms instance" for a remote name until they move onto the API.
- **Action**: if you list several `server.urls` entries for failover, name them and select one explicitly. Docs: [`ctxt instance`](../ctxt/api-cli.md#ctxt-instance).

#### Upgrade banner from the API response

- **Header.** While an upgrade is in progress or has failed, dpkms sets `X-Dpkms-Upgrade` on every `/api/v1` response, as an RFC 8941 dictionary: `state=in_progress, bucket=reingest_selective, done=47, total=120, eta=32`. A failed run adds `error="…"` (printable ASCII, at most 256 bytes), an `embeddings_migrate` run adds `target="…"`, and a run with skipped objects adds `failed=N`. Idle instances send no header. Protected and public instances send it only to authenticated callers, the same as the upgrade field on `/healthz`.
- **Banner.** `ctxt` and the `dpkms` client commands (`healthcheck`, `pipeline`, `step`) print `ℹ ctxt: upgrading <bucket>; <done>/<total> objects (<pct>%); ETA <eta>s; details: ctxt upgrade status` (or the `✗ … upgrade failed` line) on stderr from the first response that carries the header, once per command. It shows the state of the instance the command calls, local or remote.
- **Removed.** Neither CLI reads `upgrade-state.json` next to the local pidfiles any more. `dpkms` commands that work on the local store (`job`, `backup`, `restore`, `housekeeping`, …) print no banner; check `dpkms healthcheck` or `ctxt upgrade status` for the upgrade state. The daemon and the local `ctxt upgrade run` still write the file, but nothing reads it.
- **Hidden.** `--quiet`, `--no-hints` or a stderr that is not a terminal (pipes, CI, agents) hides the banner. Commands that don't call the dpkms API never print it. `ctxt status`, `ctxt upgrade status` and `dpkms healthcheck` read `/healthz`, which carries no header; they show the upgrade state in their own output.

#### Enqueue without a local fallback

- **No local queue.** `ctxt analyze`, bare `ctxt` fed on stdin or the clipboard, `ctxt capture tabs` and `ctxt capture history` send only to the one instance ctxt resolves. When nothing answers there they exit 70 (`PREREQUISITE`); when it answers 401 or 403 they exit 5 (`UNAUTHORIZED`) and the request is not retried. Before, both cases enqueued into a local `db.sqlite` and printed `Queued locally; the job will run when the daemon starts`, and a remote daemon never saw those jobs.
- **Removed**: the `Queued locally` message, the `queued_locally` field of the `capture tabs` / `capture history` JSON, the `(queued locally)` note in their listings, and the CLI's database lock on that path.
- **Batches stop on the first 70 or 5.** `capture tabs` and `capture history` print their report, then exit with that code. The URLs they never attempted show as `not sent N` in the summary and `would_send` in the JSON. Other failures (a 5xx, a refused URL) are still recorded per URL, and the run goes on and exits 1.
- **`analyze` errors follow ADR-077**: a request the instance refuses (a 422 for an unrouted type or pipeline) exits 2 instead of 1, with the instance's message; a 5xx exits 6.
- **History position per instance.** The position file keys each browser profile by instance: the `server.urls` entry's name, else its URL. Capturing into one instance, then another, sends the full window to the second. The file is now version 2. A version-1 file stops `capture history` with exit 3 (`unsupported position file version: version 1`) and is never converted or rewritten; `--reset-position` can't read it either. The JSON `position` block gains `instance`, and `--reset-position` resets the resolved instance only.
- **Unchanged**: `ctxt capture [source]` already exited 70 or 5; `list --q` still falls back to a local search for now.
- **Action**:
  - Delete the position file once: `browserhistory.state` under `$XDG_STATE_HOME/ctxt/ambient/` (see [Saved position](../manual/workflows/browser-history-capture.md#saved-position); `ctxt capture history -V` prints the path). The next plain run per browser profile reads back `capture.history.initial_lookback`; pages the instance already has are deduplicated.
  - Scheduled captures (`ctxt capture schedule`) and scripts now fail while the instance is down: check their exit status.
  - A local `db.sqlite` left by earlier fallbacks is read by nothing. Capture its content again if you need it.
