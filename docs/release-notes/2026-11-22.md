## Highlights

### Opt-in pod-backed daemon runner (`daemon.runner: pod`)

- **Ambient daemon (`ctxt capture --ambient`)** and **server lifecycle (`dpkms serve`, `dpkms ps`, `dpkms shutdown`)** can now adopt an existing pod via the standalone `pod` CLI by setting `daemon.runner: pod` in user config or passing `--runner pod --pod <name>`.
- **Local default unchanged:** When `daemon.runner` is `local` (default), `pod` is never searched on `PATH` and no pod code executes. When `runner=pod` is requested without `pod` installed, commands exit with code `70` (`PREREQUISITE`) and never silently fall back to local execution.
- **Security & isolation:** Project-layer config files (`.contexthelp/ctxt.yaml`, `.contexthelp/dpkms.yaml`) are refused if they set `daemon.*`. Remote `dpkms serve` launches always enforce `--runner local` and include `127.0.0.1` in `server.allowed_hosts` for loopback forwarding.
- See [`docs/pod-runner.md`](../pod-runner.md) for setup, lifecycle, and cost guardrails.

### Opt-in pod-backed ingestion job executor (`jobs.executor: pod`)

- **Ephemeral Stage 1 offload:** `dpkms serve` can route allowlisted ingestion job topics (`ingest:document`, `ingest:image`, `ingest:audio`, `ingest:video`, `ingest:url`, `ingest:code`, `ingest:feed`, `ingest:feed_item`, `ingest:github_release`) to ephemeral pods (`pod create` → `pod upload` → `pod exec dpkms worker run-draft` → `defer pod destroy`) while the host `dpkms` remains the single authoritative writer to storage and the job queue.
- **Bounded concurrency and cost controls:** Configurable `jobs.pod.max_inflight` semaphore (default `4`), sliding-window `jobs.pod.max_pods_per_hour` cost ceiling (default `120`), and hard `jobs.pod.max_pod_duration` lifetime bound (`< jobs.stale_timeout`).
- **Break-even guidance:** Local Docker ephemeral pods add ~630 ms p50 lifecycle overhead (~2–5 s on remote sandboxes). Keep fast heuristic text jobs local; use pod fan-out for ≥ 1.5–3 s jobs locally (≥ 5–10 s on remote sandboxes) with `server.workers >= jobs.pod.max_inflight`.
- **Local default & security:** When `jobs.executor` is `local` (default), `pod` is never probed. Project-layer `.contexthelp/dpkms.yaml` files setting `jobs.executor` or `jobs.pod.*` are refused with exit code `2`.
- See [`docs/pod-job-execution.md`](../pod-job-execution.md) for configuration and break-even guidance.

## Changes by bucket

### `reingest_selective` changes

**Page text and repository README re-derived** (steps `html_cleaner` and `github_repo_mapper`, each now at version 2)

- **What changed in stored output.**
  - `html_cleaner` parses the page and keeps its main text. When the page marks its main content (`main`, `article`), cookie and navigation text outside it is dropped. The title goes to metadata.
  - `github_repo_mapper` stores a distilled README: badges, images and noise sections (sponsors, license, contributors) are gone, HTML becomes text. Code blocks are kept as they were.
  - Objects stored by earlier versions keep the old text until they are re-derived.
- **Objects affected.** Objects of these pipelines:

  | Step | Pipelines |
  |---|---|
  | `html_cleaner` | `url.generic`, `url.repo`, `url.github.issue`, `url.github.pr`, `url.github.release`, `url.github.profile`, `url.github.starred`, `url.authenticated`, `url.interactive` |
  | `github_repo_mapper` | `url.github.repo` |

- **What the daemon does by itself.** At the next start, for each affected pipeline that calls no model or only local ones, the daemon fetches each page or repository again, under the refresh guard, and replaces the stored text. It pauses between two objects (`upgrade.rederive.pause`, default `2s`). Progress shows in `ctxt upgrade status`.
- **What to expect.**
  - The first start sends a request to the host of every captured URL of these pipelines. A repository is fetched from the GitHub API.
  - Without a GitHub token the API allows 60 calls an hour. A rate limit is a try, never counted against an object. Five tries in a row stop that pipeline's group until a later start.
  - GitHub issue, PR, release and profile pages are fetched as pages (`url_fetcher`, page rule, not the API rule). They change over time, so many refreshes are rejected and left as captured. Each rejection is a try, so such a group often stops after five in a row and moves on a few objects per start.
  - A stored page too short to compare is not fetched and is left as captured (skip `refresh_rejected`).
  - PDFs captured by URL are refused (skip `refused`).
  - A page that is gone, has changed since it was captured, or redirects to another host is left as captured.
  - Skips are shown as counts by reason, not per object.
- **What it does not do.**
  - A pipeline with a hosted, unknown or unavailable provider is deferred and listed by `ctxt upgrade status`. Its objects keep their text.
  - With the browser off, `url.authenticated` and `url.interactive` objects stored before this version do not count as stale and are not listed anywhere. With `browser.enabled: true`, the browser fetch (`ibr_fetcher`) counts as an unknown provider: the group is deferred and shown by `ctxt upgrade status`.
  - `ctxt upgrade run` cannot apply either change. It re-derives from stored content only, skips `html_cleaner`, refuses `url.github.repo` (the mapper needs the fetch) and never stamps a signature. The deferred objects stay stale.
- **Expected cost.** Per object: the pause, plus the fetch (for `url.github.repo`, two GitHub API calls, repository and README, more on a retry; without a token GitHub allows 60 calls an hour, about 30 repositories), plus the time of the local models the pipeline's LLM steps call. Wall-clock is about `N × (pause + fetch time + model time)` for `N` stale objects; with the default pause, `(N − 1) × 2s` is the floor.
- **Hold it back.** Set `upgrade.rederive.enabled: false` before the first start of this version. Nothing is scheduled then; stale objects stay as stored.
- **Operator action.** None.
