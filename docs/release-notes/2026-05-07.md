## Changes by bucket

### `reingest_selective` changes

#### `fix(search): hyphen crash + bullet items invisible to FTS` — T-0565

- **What changed**: `internal/projection/projection.go` `ProjectIndex` falls back to flat fields when the graph branch yields no Summary/Section content. Plus `internal/search/safe_fts.go` adds query sanitisation against FTS5 operator-injection (hyphens, colons, etc.).
- **Selector predicate**: `pipeline LIKE 'text.short@v1' AND graph_json IS NOT NULL AND graph_json NOT LIKE '%"node_type":"summary"%'`
  - Translated: objects routed to the (now-versioned) `text.short@v1` pipeline whose graph carries Tag/EntityMention nodes but no Summary node. These are the documents whose body lived only in `TextContent` and was therefore invisible to FTS pre-fix.
- **Versioned pipeline?**: **No** (retroactively — the versioning convention is being adopted in this same release per ADR-070; legacy objects are stamped `@v0` and the post-fix `text.short` becomes `@v1`). For future fixes of this shape, the answer must be **yes**: gate behind a new `@vN`.
- **Estimated wall-clock**: ~50ms/object × affected count. For a typical corpus (<10K objects), most are not affected; running `ctxt upgrade plan` first is the responsible move.
- **Estimated LLM cost**: **$0** — this is a projection-only change. No new embeddings, no LLM inference. The re-ingest re-runs `entity_extractor` over `RawContent` and rewrites `projected_fts_body` from the corrected `ProjectIndex`.

**Verification (ben suite)**: not retroactively measured. Going forward, this kind of fix lands with a `suites/recall-text-short.ben.yaml` row showing pre/post recall on the affected subset. The test suite added in commit `232cd8f` proves correctness on a representative fixture (`TestFindByText_GraphWithoutSummaryIndexesListItems`), but is unit-level rather than corpus-level.

## Upgrade walkthrough

### Step 0 — Back up before upgrading

```bash
ctxt backup create --to ~/ctxt-backups/pre-2026-05-07.tar.gz
```

### Step 1 — Pull / install

```bash
# however you install, e.g.:
git pull && make install
```

### Step 2 — Rename config file (T-0576)

```bash
# If you run dpkms (most common):
mv ~/.config/contexthelp/config.yaml ~/.config/contexthelp/dpkms.yaml

# If you have ctxt-only config (rare):
# mv ~/.config/contexthelp/config.yaml ~/.config/contexthelp/ctxt.yaml
```

### Step 3 — Plan the selective re-ingest (T-0565)

```bash
# Dry-run first to see what's affected:
ctxt upgrade plan
```

> **Note**: `ctxt upgrade plan` is **not yet implemented** as of this release — the framework lands with ADR-070 but the runtime CLI is filed as follow-up tasks (T-NEW-1 through T-NEW-3). Until those land, the selective re-ingest is best done manually:
>
> ```bash
> # List affected objects:
> ctxt find '*' --filter pipeline=text.short --json | jq '.results[] | select(.graph.summary == null) | .id'
>
> # Re-analyze each:
> ctxt analyze --reanalyze <id>
> ```
>
> Once `ctxt upgrade plan` ships, this manual workaround is replaced by the supported flow.

### Step 4 — Run the re-ingest

```bash
ctxt upgrade run --filter pipeline=text.short@v1
# or, until the runtime ships, the manual loop above.
```

### Step 5 — Verify

```bash
ctxt upgrade status --watch  # (post-runtime)
# or:
ctxt find SageMaker  # the original repro from T-0565 — should now return hits
```

## Notes

- The retroactive labelling here is a one-time exercise to seed the format. From this release forward, every PR fills in the table at PR time, not after the fact.
- The two `reingest_selective` ADRs (ADR-070, ADR-071) are themselves marked `none` because they're documents — their *implementation* tasks (T-NEW-*) will be the ones marked `reingest_*` if and when they ship operator-impacting code.
- The user-facing rename in T-0576 is `none` per ADR-070's strict definition: the daemon does not re-ingest or reindex, the operator does a one-shot file move. We keep it visible here under the table because it *is* operator-affecting work, just not in a way the upgrade taxonomy claims jurisdiction over. Future ADRs may revisit whether the taxonomy should grow a fourth bucket for this shape.
