## Changes by bucket

### `reindex_auto` changes

#### `feat(storage,pipeline): index_signatures table + pipeline_version stamping` — T-0579

- **What changed**: established the signature substrate (Part A) + pipeline_version
  string convention (Part B) for bucket-1 detection. First daemon startup
  computes and stores the signature; future signature changes will trigger
  the reindex_auto flow (T-0581 ships the actual rebuild worker).
- **Signature bump**: n/a (first install — no prior signature).
- **Estimated rebuild wall-clock**: 0s (no rebuild this release; storage
  scaffolding only).

### `reingest_selective` changes

#### `feat(upgrade): selective re-ingest engine + staleness warning` — T-0581

- **What changed**: ships the runtime behind the `ctxt upgrade run` stub from
  T-0580. New `internal/upgrade/{selector,worker}.go` parses
  `--filter pipeline=<name>@vN` (or `--where <pred>`) into a SQL predicate,
  iterates the matching set deterministically, and re-runs the registry's
  current pipeline against each object's `RawContent` via the new
  `Service.ReanalyzeObject`. The upgrade-state machine from T-0580 ticks
  through Start → Tick(N) → Complete so `ctxt upgrade status` (and the CLI
  banner) reflect live progress. `ctxt upgrade plan` is now predicate-driven
  too: iterates the registry, counts rows per family below current version,
  emits the (from→to) table with the exact `--filter` invocation per row.
- **Selector predicate**: `pipeline=text.short@v0` (the canonical example —
  any object whose stored `pipeline` stamp parses to a version older than
  the registry's currently-installed version qualifies). The `--where`
  escape hatch supports complex selectivity like
  `where:graph_json IS NULL AND pipeline LIKE 'text.short%'`.
- **Versioned pipeline?**: **Yes**. The `@vN` convention is now load-bearing
  — bare `--filter pipeline=text.short` is rejected at parse time so an
  operator can't accidentally re-ingest every version of a family.
- **Operator-Impact reason**: this is the FIRST release where
  `ctxt upgrade run` actually does work. T-0565 (search hyphen crash + bullet
  items invisible to FTS) shipped its `ProjectIndex` fix before the upgrade
  taxonomy existed; the operator-facing path to re-ingest those affected
  objects has been the manual `ctxt analyze --reanalyze <id>` loop. Once
  T-0581 lands, the supported flow is `ctxt upgrade plan` to discover what's
  pending, then `ctxt upgrade run --filter pipeline=text.short@v0` to clear
  it. The first time an operator runs this on a corpus that pre-dates the
  registry bumping `text.short` past `@v0`, the worker executes the
  pending re-ingest backlog from T-0565 onwards.
- **Estimated wall-clock**: ~50ms/object × pending count (matches T-0565's
  per-object cost since this re-runs the same pipeline against the same
  RawContent).
- **Estimated LLM cost**: **$0** for projection-only re-ingests — the worker
  surfaces a per-object cost field, but the current pipelines (`text.short`,
  `text.long`) don't call LLMs during re-analysis. Future LLM-driven
  pipelines will populate the cost meter; the `--budget USD` flag is wired
  to abort cleanly when the cumulative cost exceeds the cap.
- **Soft staleness signal**: search responses now carry
  `diagnostics.staleness_warning.{count,reason}` when one or more candidates
  are stamped with an older version than the registry's current. Search
  still returns the (possibly stale) results — the warning prompts the
  operator toward `ctxt upgrade plan`. `ctxt find` renders this as a
  `Note:` line under the results table.
- **Bus topics added** (ADR-070 §6, 4-segment past-tense):
  `dpkms.upgrade.plan.computed`,
  `dpkms.upgrade.reingest.{started,progressed,completed,failed}`.

#### `fix(search): hyphen crash + bullet items invisible to FTS` — T-0565

- **What changed**: `internal/projection/projection.go` `ProjectIndex` falls back to flat fields when the graph branch yields no Summary/Section content. Plus `internal/search/safe_fts.go` adds query sanitisation against FTS5 operator-injection (hyphens, colons, etc.).
- **Selector predicate**: `pipeline LIKE 'text.short@v1' AND graph_json IS NOT NULL AND graph_json NOT LIKE '%"node_type":"summary"%'`
  - Translated: objects routed to the (now-versioned) `text.short@v1` pipeline whose graph carries Tag/EntityMention nodes but no Summary node. These are the documents whose body lived only in `TextContent` and was therefore invisible to FTS pre-fix.
- **Versioned pipeline?**: **No** (retroactively — the versioning convention is being adopted in this same release per ADR-070; legacy objects are stamped `@v0` and the post-fix `text.short` becomes `@v1`). For future fixes of this shape, the answer must be **yes**: gate behind a new `@vN`.
- **Estimated wall-clock**: ~50ms/object × affected count. For a typical corpus (<10K objects), most are not affected; running `ctxt upgrade plan` first is the responsible move.
- **Estimated LLM cost**: **$0** — this is a projection-only change. No new embeddings, no LLM inference. The re-ingest re-runs `entity_extractor` over `RawContent` and rewrites `projected_fts_body` from the corrected `ProjectIndex`.

**Verification (ben suite)**: not retroactively measured. Going forward, this kind of fix lands with a `suites/recall-text-short.ben.yaml` row showing pre/post recall on the affected subset. The test suite added in commit `232cd8f` proves correctness on a representative fixture (`TestFindByText_GraphWithoutSummaryIndexesListItems`), but is unit-level rather than corpus-level.

### `none` changes (no operator impact)

- **`493e469` (T-0576)** — config-file rename. Operator must rename `~/.config/contexthelp/config.yaml` → `~/.config/contexthelp/dpkms.yaml` (or `ctxt.yaml` if they were running ctxt-side config), but no daemon-managed re-ingest or reindex.
- **ADR-070** — framework only. No code changes that affect stored knowledge or the index.
- **ADR-071** — design document only. Implementation is gated on three preconditions (ADR-071 §Three preconditions) that have not yet been met.
- **`23b0978` (T-0580)** — `ctxt upgrade {status,plan,run}` CLI surface, `/healthz` upgrade envelope, banner middleware. Additive only: existing `/healthz` consumers see byte-identical payloads when no upgrade is in flight (the `upgrade` field is omitempty), and the new CLI subcommands don't touch stored knowledge or the pipeline contract. `run` is intentionally a refuse-stub pointing at T-0581.

## Upgrade walkthrough

### Step 0 — Back up before upgrading

```bash
ctxt backup create --to ~/ctxt-backups/pre-2026-05-07.tar.gz
```

### Step 1 — Pull / install

```bash
# however you install, e.g.:
git pull && make install
```

### Step 2 — Rename config file (T-0576)

```bash
# If you run dpkms (most common):
mv ~/.config/contexthelp/config.yaml ~/.config/contexthelp/dpkms.yaml

# If you have ctxt-only config (rare):
# mv ~/.config/contexthelp/config.yaml ~/.config/contexthelp/ctxt.yaml
```

### Step 3 — Plan the selective re-ingest (T-0565 + T-0581)

```bash
# Dry-run first to see what's affected:
ctxt upgrade plan
```

T-0581 ships the predicate-driven plan — the output looks like:

```
Upgrade plan:
  reindex_auto:
    objects_fts: signature ok (no rebuild needed)
  reingest_selective:
    text.short@v0 → text.short@v1: 47 objects
      Run: ctxt upgrade run --filter pipeline=text.short@v0
  reingest_all:
    none

Total objects pending: 47
```

If your `text.short` pipeline registration hasn't been bumped past `@v0` (a
fresh corpus, or a corpus that never had T-0565 applied retroactively), the
selective row will be `none`. Run `ctxt upgrade plan` after upgrading to
this release to confirm what your specific corpus needs.

### Step 4 — Run the re-ingest

```bash
ctxt upgrade run --filter pipeline=text.short@v0 --dry-run   # confirm match count
ctxt upgrade run --filter pipeline=text.short@v0             # execute
```

### Step 5 — Verify

```bash
ctxt upgrade status --watch  # tracks Start → Tick → Complete in real time
# or:
ctxt find SageMaker  # the original repro from T-0565 — should now return hits
```

If your search results also include a `Note:` line about objects pending
upgrade, that's the new T-0581 staleness signal — re-run `ctxt upgrade plan`
to see what's still pending and `ctxt upgrade run --filter ...` to clear it.

## Notes

- The retroactive labelling here is a one-time exercise to seed the format. From this release forward, every PR fills in the table at PR time, not after the fact.
- The two `reingest_selective` ADRs (ADR-070, ADR-071) are themselves marked `none` because they're documents — their *implementation* tasks (T-NEW-*) will be the ones marked `reingest_*` if and when they ship operator-impacting code.
- The user-facing rename in T-0576 is `none` per ADR-070's strict definition: the daemon does not re-ingest or reindex, the operator does a one-shot file move. We keep it visible here under the table because it *is* operator-affecting work, just not in a way the upgrade taxonomy claims jurisdiction over. Future ADRs may revisit whether the taxonomy should grow a fourth bucket for this shape.
