# Localization & Internationalization (L10N & I18N)

ContextHelp is inherently language-agnostic, but full localization and internationalization capabilities are provided **optional** through a dedicated I18N/L10N plugin system. This document defines how multi-language support works, what is handled by default, and how plugins can extend the engine to deliver translated summaries, language-specific indexing, translated tags, and user-configurable language preferences.

---

## Goals

Localization and internationalization features aim to:

- Allow users to work with **content in any language**.
- Permit users to define **preferred language(s)** for output.
- Support **automatic or manual translations** of summaries, tags, and sections.
- Provide **CLI and API language filters**, including original-language filtering.
- Allow registries to supply translated labels, or allow **user overrides**.
- Keep the **core schema free of language dependencies**, making L10N/I18N optional and decoupled.
- Enable third-party developers to build plugins for translation, multi-language retrieval, and machine-assisted localization.

---

## Design Principles

### 1. **Language Is Metadata, Not Schema**
The base bookmark schema remains unchanged and language-agnostic.

A plugin may add fields such as:
- `language` (detected or user-specified)
- `translations.summary`
- `translations.sections`
- `translations.tags`
- `translations.title`

But the canonical schema does **not** require these fields.

### 2. **User-Defined Preferences Drive Behavior**
Users configure:

- Preferred languages (ordered list)
  e.g. `["fr", "ar", "en"]`

- Whether to enable automatic translation
- Whether summaries should be rewritten in the preferred language
- Translation providers (local models, APIs, registries, etc.)

The engine always attempts to serve content in the user's **primary preferred language** where possible.

### 3. **Plugins Provide the Functionality**
By default, ContextHelp does:
- Language detection (optional, pipeline-level)
- No translation
- No multi-language transformation
- No localization of tag labels

An **I18N plugin** may extend:

- Storage schema (e.g., adding translation maps)
- Pipelines (translation steps)
- Registries (translated taxonomy labels)
- CLI behavior (language flags)
- API middleware (content negotiation)
- Agents (language-aware context generation)

### 4. **Translations Are Views, Not Rewrites**
The original text is **preserved**.

Translations are additional layers accessed based on user preferences or request parameters.

## User Preferences

Example configuration:

```yaml
i18n:
  enabled: true
  preferredLanguages:
    - "fr"
    - "en"
  autoTranslate: true
  translateSummaries: true
  translateSections: true
  translateTags: true
  provider: "openai"    # or "local-llama", "registry-service", "plugin-x"
  skipOnAnalyzeDefault: false
```

Behavior:

- If content is not in one of the preferred languages:
  - Summaries are translated.
  - Tag labels are translated (if available).
  - Missing translations can be generated automatically.

- If content *is* in a preferred language:
  - Summaries remain as-is unless user forces translation.
  - Tags are localized if registry or user provides translations.

## Pipelines: Language-Aware Processing

Pipelines can become I18N-aware when the plugin is installed:

### Input Stage
- Accepts `--lang <code>` to override detection.
- Optionally detects language at ingestion using a model or registry.

### Processing Stage
- Summaries can be auto-translated.
- Sections can be translated in parallel.
- OCR and ASR steps use language-specific models when available.

### Output Stage
Plugins may add fields such as:

```json
{
  "language": "es",
  "translations": {
    "fr": { "summary": "...", "sections": [...] },
    "en": { "summary": "...", "sections": [...] }
  }
}
```

---

## Registries & Tag Translation

Registries may provide:

- Canonical tag labels (usually English)
- Optional localized labels, e.g.:

```json
{
  "label": "ui.hero.antipattern",
  "aliases": {
      "fr": "anti-modèle de héros UI",
      "es": "antipatrón de héroe UI"
  }
}
```

Users may:

- Override registry translations
- Add missing translations
- Create translation plugins (e.g., querying a translation API)

When no translation is available, the plugin may fallback to:

- Machine translation
- Canonical label
- LLM-based paraphrasing

## Retrieval & Filtering by Language

### CLI Options

#### `--orig-lang <code>`
Filter bookmarks by the **original** language of the content.

#### `--prefer-lang <code>`
Force output to this language for the current command.

#### `--translate none`
Skip translations entirely for this execution.

#### `--lang <code>` during `analyze`
Specify the input language explicitly.

### Examples

```bash
ch list --orig-lang es
ch list --prefer-lang fr
ch analyze --lang ar file.txt
ch analyze --translate none
```

---

## API Integration

### REST
`GET /bookmarks?origLang=es&preferLang=fr&translate=auto`

### gRPC
Fields such as:

```protobuf
string original_language_filter = 12;
string preferred_language = 13;
bool skip_translation = 14;
```

### Content Negotiation
If desired, the API may inspect `Accept-Language` headers, but defaults still use user config.

---

## Plugin Responsibilities

The I18N plugin is responsible for:

- Language detection (if not overridden)
- Translation routing
- Maintaining translation caches
- Augmenting bookmark schema when storing translations
- Hooking into pipeline stages:
  - pre-analysis (detect / override language)
  - post-summary-generation (translate)
  - post-tag-generation (translate)
- Hooking into query layer:
  - auto-substitution of localized views
  - fallback logic
- Registry translation merging and overrides

It must ensure:

- Original raw content is untouched
- Translations are clearly separated
- User preferences override everything
- Performance impact is controlled (optional caching, batching)

---

## Limitations & Notes

- Translation quality depends on the configured provider.
- Very large content may require chunking strategies.
- Registries may not offer translations; plugin must handle fallback gracefully.
- Multi-language search may require embeddings or language-specific analyzers.
- Some pipelines may yield language-dependent behavior (e.g., grammar-based analysis).

---

## Summary

Localization and internationalization in ContextHelp is:

- **Optional**, handled by plugins
- **Flexible**, supporting multiple languages simultaneously
- **User-driven**, with preferred language lists and overrides
- **Extensible**, enabling custom translation providers
- **Non-destructive**, preserving originals and augmenting with translations

The plugin mechanism ensures that L10N/I18N integrates cleanly with every part of the engine—from pipelines to registries to CLI/API—without polluting the core schema or forcing unnecessary defaults.
